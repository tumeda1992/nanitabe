# コード設計原則

## 実装コストを理由にユーザー体験を変えてはならない

実装変更の提案前に、その変更がユーザー体験（機能・振る舞い）に影響するかを確認すること。

- 体験が変わらない（内部実装の置き換え・リファクタリング）→ 既存コードの削除・統合を許容
- 体験が変わる（機能・振る舞いが変わる）→ 実装コストを理由に変更してはならない

やってしまいがちな失敗: 「これを消せば実装が楽になる」という理由で、ユーザーが使っている機能・要素を削除する案を出す
→ 正しい問い: 「この変更はユーザーが体験できることを変えるか？」→ Yes なら実装コストは理由にならない

## 共通化（抽出）の判断基準

コードが同一に見えることは、共通化の十分条件ではない。

判断の問い: **「Aの要件が変わったとき、Bも同じ理由で変わるべきか？」**
- Yes（変更の必然性がある）→ 抽出して共通化する
- No（独立したコンテキストにある）→ たとえ同一コードでも別々に持つ

同一コードなのに抽出しないのはなぜか:
- 共通化した瞬間に独立していた2つが依存関係を持つ
- 片方の要件変更が他方に波及し、意図しない変更が必要になる
- 差異を吸収するためにオプション・分岐が生えて関数が肥大化する
- 「やはり分けよう」となったとき、使用箇所を探して剥がす作業が発生する

コードの重複はコストだが、誤った抽出はより高いコストになる。

やってしまいがちな失敗（逆パターン）: 「コンテキストが違う」「実装が少し違う」という理由で、変更タイミングが同じコードをコピペ展開する
→ 同じ理由で同じタイミングで変わるコードが2箇所にあると、片方の変更漏れが起きる
→ 判断の問い: 「このコードを変えるとき、もう一方も必ず同じ理由で変わるか？」→ Yes なら抽出する

## features ディレクトリ構造

`features/` の配置はバックエンドのドメインモジュール階層を反映する。

| バックエンド | フロントエンド |
|---|---|
| `Meal::*` | `features/meal/` |
| `Meal::Frame::*` | `features/meal/frame/` |
| `Meal::Frame::Pattern::*` | `features/meal/frame/pattern/` |

やってしまいがちな失敗: 新しいサブドメイン機能を `features/` 直下にフラットに置く
（例: `features/mealFramePattern/` をトップに置く）
→ バックエンドの階層との対応が崩れ、次の機能追加時に置き場所の判断が困難になる

各 features ディレクトリの hook facade パターン（`useDish.ts` など）については `features/dish/README.md` を参照すること。

## components ディレクトリ構造

`components/` の配置も `features/` と同じ階層を反映する。

| バックエンド | フロントエンド（features） | フロントエンド（components） |
|---|---|---|
| `Meal::*` | `features/meal/` | `components/meal/` |
| `Meal::Frame::*` | `features/meal/frame/` | `components/meal/frame/` |
| `Meal::Frame::Pattern::*` | `features/meal/frame/pattern/` | `components/meal/frame/pattern/` |

やってしまいがちな失敗: 新しいサブドメイン機能のコンポーネントを `components/` 直下にフラットに置く
（例: `components/mealFramePattern/` をトップに置く）
→ `features/` との対応が崩れ、次の機能追加時に置き場所の判断が困難になる
→ 正しい問い: 「このコンポーネントが属するバックエンドモジュールはどのレベルか？」
