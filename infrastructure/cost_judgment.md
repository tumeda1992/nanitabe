# 費用の判断

AWS resource を構成へ含めるかどうかを、金額を根拠に判断するための基準。

## 何を判断する document か

**対象**: 「この resource を構成へ入れるか」を金額で決める場面。入れると固定費が増えるが、入れないと損失のリスクが残る、という形の判断。

**対象外**: 既に構成が決まったものを安くする作業。instance size の見直しや Savings Plans の検討はここでは扱わない。

## 課金モデルを分けて考える

課金の発生の仕方が違うものを同じ基準で扱うと判断を誤る。まず型を見分ける。

### 時間課金 — 存在するだけで積み上がる

ALB、RDS、NAT Gateway、Elastic IP。**使っていない時間も払う。**

止める手段が無いか、止めても課金が続く。Elastic IP は「どこにも割り当てていない間」に課金される。RDS は停止しても 7 日で自動起動する。

この型の resource は、入れた時点で月額が確定する。構成へ含めるかどうかが、そのまま費用の判断になる。

### 保存・件数課金 — 量に比例し、設定で抑えられる

ECR の image、CloudWatch Logs、CloudWatch alarm。

量が増えれば増えるが、量を抑える設定がある。
ECR は lifecycle policy で世代を絞れる。CloudWatch Logs は retention で保持期間を決められる。alarm は個数で決まる。

この型は「入れるか入れないか」ではなく「どれだけ持つか」の判断になることが多い。

## 判断の手順

### 1. 防ぐ対象の損失を見積もる

その resource が防ぐ損失を、金額と期間で出す。「なんとなく危ない」で止めない。

例: Fargate task（0.25 vCPU / 0.5 GB）の止め忘れは $0.012/時間。

| 気づくまで | 損失 |
| --- | --- |
| 1 日 | $0.29 |
| 3 日 | $0.86 |
| 1 週間 | $2.0 |
| 1 か月 | $8.6 |

気づくまでの期間は、その環境の使用頻度から見積もる。週 1 回使う環境なら数日、月 1 回なら数週間になる。**使用頻度が低いほど気づくのが遅れ、損失が大きくなる。**

### 2. 手段を複数出す（1 つ思いついた時点で決めない）

同じ目的を達成する手段が複数あり、**額が桁で違うことがある。**

例: ECS task の止め忘れを検知する。

| 手段 | 月額 | 備考 |
| --- | --- | --- |
| Container Insights の `RunningTaskCount` を監視 | $3〜$6 | custom metric として課金される。metric あたり $0.30、service あたり 10〜20 個 |
| 標準 metric（`CPUUtilization`）の data point 有無で判定 | $0.10 | alarm 1 個ぶん。標準 metric に課金は無い |

どちらも「task が動き続けているか」を判定する。最初に思いついたほうを採ると 30 倍以上の差が出る。

### 3. 損益分岐で比べる

防ぐための固定費と、防ぐ対象の損失を並べる。

例: alarm 1 個は年 $1.2。止め忘れは 3 日で $0.86。**年 1〜2 回、数日規模の止め忘れが起きるなら釣り合う。**

釣り合わない場合でも、損失が「金額以外の損害」を含むなら別途判断する。ここで扱うのは金額で比較できる部分だけである。

## サービス別の要点

触ったサービスの、判断に効く性質を記録する。

### ECS / Fargate

- task が存在しない間（`desired_count = 0`）は課金されない。起動している時間だけ払う。
- ARM64 は X86_64 より約 20% 安い。
- cluster 自体に固定費は無い（Fargate のみを使う場合）。

### CloudWatch

- **標準 metric に課金は無い。** `AWS/ECS` の `CPUUtilization` や `MemoryUtilization` はそのまま使える。
- alarm は 1 個あたり月 $0.10。
- Container Insights は custom metric として課金される。
  ECS では service あたり 10〜20 個の metric が出るため月 $3〜$6 になる。
  `RunningTaskCount` のような標準 metric に無い値が要るとき以外は避ける。
- Logs は取り込み（$0.76/GB）が主で、保存（$0.03/GB/月）は小さい。
  **取り込みは書き込んだ時にしか発生しない**ため、停止中の課金は保存分だけになる。
  retention を切るかどうかは、運用上 log を残す価値と保存料を比べて決める。

### ECR

- image の保存に $0.10/GB/月。Rails の image は 1 GB 前後。
- lifecycle policy で世代を絞れる。動作確認環境のように最新だけあればよいなら 1 世代に限定する。

### API Gateway

- HTTP API にはリクエスト課金しか無い（$1.00/100 万リクエスト）。**存在するだけの固定費が無い。**
- custom domain と ACM 証明書にも課金は無い。
- ALB の代わりに HTTPS 終端として使える場面がある。ALB が月 $18 程度の時間課金であるのに対し、こちらは使わなければゼロになる。

### Secrets Manager / SSM Parameter Store

- Secrets Manager は secret 1 件あたり月 $0.4 の固定課金。
- SSM Parameter Store の Standard parameter は無料。AWS managed key による SecureString の暗号化にも課金は無い。
- ECS の task definition が `secrets` として参照できるのはこの 2 つだけであり、固定費を避けるなら SSM を選ぶ。

## やってしまいがちな失敗

### 「常時課金の resource を含めない」で少額の resource まで退ける

**やってしまいがちな判断**: 要件に「停止中に課金が発生する resource を構成へ含めない」と書き、その文言だけを根拠に月 $0.10 の alarm を退ける。

**何が起きるか**: 止め忘れを検知する手段が無くなる。月 $0.10 を惜しんで、月 $8.6 の損失リスクを残すことになる。

**正しい問い**: 「この resource が防ぐ損失は、この resource の固定費より大きいか」。禁じたいのは無駄な常時課金であって、損失を防ぐ少額の resource ではない。

要件へ金額の上限を書く場合は、resource の種類ではなく金額で書く。
「時間課金の resource を含めない」ではなく「停止中の課金を月 $1 以内に収める」とすれば、
少額で価値のある resource を機械的に退けずに済む。

### 同じ目的の手段の額を比べずに 1 つ目で決める

**やってしまいがちな判断**: 「task の数を監視したい」から `RunningTaskCount` を探し、Container Insights が要ると分かってそのまま有効化する。

**何が起きるか**: 月 $3〜$6 が発生する。標準 metric の data point 有無で同じ判定ができることに気づかない。

**正しい問い**: 「この判定は、課金の無い手段では実現できないか」。監視したい値そのものが無くても、その値の代理になる観測があることが多い。
