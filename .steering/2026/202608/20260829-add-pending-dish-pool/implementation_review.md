# 議論記録

## 論点1: 自由記述データを「引き継ぐ意味がない」と推測で判断した原因

**ステータス:** 分解済み

**種別:** 認識齟齬

### イテレーション0: 原因ownerの一般則を確定する

#### 提案0

**判断の対象:** `task-design` skill へ、設計時に問うべき2つの問いを追加する。

##### 追加する問い1: 自由記述データを推測で捨てない

> 判断の問い: **「そのデータに何が書かれるかを、設計者が列挙できるか」**
>
> - 列挙できる（enum、フラグ、参照、日付等）→ 意味から引き継ぎ要否を判断してよい
> - **列挙できない（ユーザーが自由記述したテキスト）→ 保持する側へ倒す。捨てる判断にはユーザーの明示合意を要する**
>
> やってしまいがちな失敗: 自由記述欄に何が書かれるかを設計者が推測し、「この文脈では意味を持たない」と結論して捨てる
> → 自由記述はユーザーが用途を決める領域であり、設計者の推測は当たらない。捨てる判断はユーザーだけができる
> → 正しい問い: 「私はこの欄の中身を知っているか。それとも書かれそうな内容を想像しただけか」

##### 追加する問い2: 喪失の警告は、喪失を正当化しない

> 判断の問い: **「この設計を成立させるために、データ喪失の警告をUIへ足そうとしていないか」**
>
> 足そうとしているなら、警告文を書く前に、その喪失を設計で避けられないかを先に問う。
>
> やってしまいがちな失敗: 設計上データが失われることに気づき、確認ダイアログへ「〇〇は失われます」と書いて解決したことにする
> → 警告が必要になったこと自体が、その喪失が受け入れられていない証拠である。ユーザーに告知しても、失われて困る事実は変わらない
> → 正しい問い: 「なぜ警告が要ると感じたのか。それは喪失が許容できないと自分でも思っているからではないか」

##### 適用先

`tumeda-dev` plugin の `task-design` skill。repositoryを問わず成立する設計processの問いであるため。
このrepositoryの docs ではない。

適用は `escalate-plugin-skill-fix` で正本repositoryへ引き渡す（論点9で確立した経路）。

#### 提案背景

##### 起点となったfeedback

ユーザーの動作確認後に受領した。

> 確認したけど、いい感じだったよ。かなりいいけど、触ってみて仕様追加したくなった。延期した時、食事コメントも退避したい。meal_typeを退避したように

##### 認識齟齬と判定した根拠

`facilitate-discussion` の判定基準「このfeedbackは、提案の選好を変えたのか。それとも提案が依拠していた
前提知識の誤りを正したのか」に照らすと、後者である。

`task-design-discussion.md` 論点2で、私は `comment` を持たない理由をこう書いた。

> 食事コメントは「その日その回の食事について」の記述であり、日付を外すと対象を失う。時間帯と違い、
> 次に食べるときへ引き継ぐ意味を持たない

この判断は「食事コメントに何が書かれるか」という前提知識に依拠していた。そして私はその知識を
持っていなかった。実際には料理の作り方や意図に関するメモ（「多めに作る」「子供用に薄味」等）も
書かれうる。前提が誤っていたため、そこから導いた結論も誤った。

##### 原因ownerを skill と判定した理由

「食事コメントに何が書かれるか」自体はこのrepositoryの運用知識であり、repository知識の不足に見える。
しかしそれを `meal/README.md` へ書いても、次に別の自由記述欄（料理コメント、レシピメモ、枠名等）で
同じ誤りが起きる。列挙しきれない。

再発を防ぐのは「自由記述の中身を推測しない」という設計processの問いであり、これはrepositoryを問わず
成立する。したがって原因ownerは skill である。

##### 問い2を併せて追加する理由

問い1だけでは、今回の失敗を検出できなかった可能性が高い。私は論点2の時点で「コメントは引き継がない」と
判断し、それが誤りだと気づく機会を持たなかった。

しかし論点4で、確認ダイアログへ「（食事コメントは失われます）」と書いている。**この時点が、設計を
見直す第二の機会だった。**警告文を書くという行為は、喪失が問題であると自分でも認識していることの
表れである。私はそれを警告の追加で処理し、喪失そのものを疑わなかった。

問い1は誤りを未然に防ぎ、問い2は既に作り込んだ誤りを検出する。層が異なるため両方を置く。

##### 具体ケースの修正を先に合意しない理由

`facilitate-discussion` の `2.1.1` は「repository知識またはskillの不足では、具体ケース固有の修正を
先に合意しない。原因ownerの一般則を主decisionとして合意した後、元の具体ケースをその適用例として
必ず再評価する」と定める。

したがって、`comment` を引き継ぐという具体的な設計変更は次の論点で扱う。この論点では一般則だけを扱う。

#### 提案0へのフィードバック

**結果:** 却下。今回の具体に張り付いており汎用性がない。原因ownerの特定も誤り

> 非常に提案の質が低い。今回の具体にベッタリでまったく汎用性がない。（略）entity_modeling.md 案件。毛色が変わるから、entity_modelingをディレクトリにして、既存をcore.mdとして、退避エンティティ（historyも含む）のモデリング方法について記載する。データ退避をする、あるデータをつくって、元データを削除するようなものが退避データで、その場合、ある操作に必要最低限なデータを選ぶというより、データを落とさないことを基本方針に、落とすデータに意図を持つ考え方とする。migrationと考えは近い。

提案0の誤りは2つある。

- **抽象化の軸を誤った。**「自由記述かどうか」というフィールド単位の性質を軸にしたが、実際の分岐は
  モデリングのパターンにある。自由記述でない項目（日付、参照、フラグ）でも、退避時に落とせば同じ問題が起きる
- **原因ownerを誤った。** `task-design` skill の設計processの問いではなく、
  `entity_modeling` というモデリング標準が扱う領域である

feedbackが示した正しい軸は「**あるデータを作り、元データを削除する**」というパターンの有無である。
このパターンでは、必要最低限を選ぶのではなく、落とさないことを既定とし、落とす項目に意図を持つ。

### イテレーション1: 退避エンティティのモデリング標準として一般化する

#### 提案1

**判断の対象:** `plugins/tumeda-dev/docs/development_standards/entity_modeling.md` を directory 化し、
退避エンティティのモデリング標準を追加する。

##### 構成

```text
docs/development_standards/
  entity_modeling/
    README.md      取り回し方針。core と退避のどちらを読むか
    core.md        既存の entity_modeling.md をそのまま移す
    {退避}.md      新規。退避エンティティのモデリング
  naming/
```

`naming/` と同じ形（README + core + 対象別file）に揃える。

##### 新規fileに書く内容

**定義**

あるデータを作り、元データを削除する事象を**データ退避**と呼ぶ。作られる側を退避エンティティと呼ぶ。
history、archive、状態遷移による別テーブルへの移動がこれに当たる。

**core.md と既定が逆になる**

| | 既定 | 判断の問い |
| --- | --- | --- |
| 通常のエンティティ（`core.md`） | 持たない（opt-in） | このエンティティはこのフィールドなしで完結した意味を持つか。Yes なら追加しない |
| 退避エンティティ | **持つ（opt-out）** | この項目を引き継がないと決めた理由を書けるか。書けないなら引き継ぐ |

**なぜ逆になるか**

- 通常のエンティティで足さなかった項目は「まだ無い」だけであり、必要になれば後から足せる
- 退避エンティティで引き継がなかった項目は、元データの削除とともに**失われる**。後から足しても
  過去に退避した分は戻らない

回復可能性が非対称であるため、既定も逆にする。

**やってしまいがちな失敗**

- 退避先を「その操作に必要最低限のデータ」で設計する
  → 操作の観点では不要に見えても、元データの持ち主にとって意味のある項目が落ちる。
    操作の必要性は、元データの持ち主が何を保存したかを決める根拠にならない
- 項目が落ちることに気づき、UIへ「〇〇は失われます」と警告を出して済ませる
  → 警告は喪失を正当化しない。警告が要ると感じた時点が、既定（保存）へ戻す合図である

**migration と同じ構造**

`common_standard/function_migration_policy.md` は、移行時に全rangeを登録し、未分類の削除を失敗とする。
データ退避も同じ構造を持つ。元データの全項目を一度列挙し、引き継ぐ／落とすを分類し、
未分類の欠落を失敗とする。落とすものには理由を残す。

##### file名の候補

`naming/file.md` の規則（直上ディレクトリの文脈を継承する、同階層と足並みを揃える）に従い、
`entity` や `modeling` を重複させない。

| | file名 | 読み | 弱点 |
| --- | --- | --- | --- |
| **a** | `evacuation.md` | 退避 | データ文脈での evacuation はやや不自然 |
| **b** | `carrying_over.md` | 引き継ぎ | 元データ削除という条件が名前から読めない |
| **c** | `displacement.md` | 移設 | 一般的でない |

推奨は保留する。この3案はいずれも弱点があり、より適切な語がある可能性が高い。

#### 提案背景

##### feedbackが示した抽象化の軸

提案0は「自由記述かどうか」を軸にした。この軸では、日付・参照・フラグのような列挙可能な項目が
退避時に落ちるケースを捉えられない。今回 `comment` が落ちたのは自由記述だったからではなく、
**退避エンティティを最小構成で設計したから**である。

feedbackの「ある操作に必要最低限なデータを選ぶというより、データを落とさないことを基本方針に、
落とすデータに意図を持つ」が正しい軸を与えている。

##### 原因ownerを entity_modeling へ移す理由

提案0は `task-design` skill の設計processの問いとして扱った。しかしこれはエンティティ設計の
判断基準そのものであり、`entity_modeling` が持つべき内容である。

`entity_modeling.md`（現 `core.md`）は既にフィールド追加の既定を持つ。退避エンティティはその既定が
逆転する条件であり、同じ標準の中で対比させないと、読者は `core.md` の基準をそのまま適用してしまう。
今回私が犯した誤りがまさにそれである。

##### directory 化する理由

feedbackの「毛色が変わる」に該当する。`core.md` は「エンティティをどう切るか、どう名付けるか」という
汎用の判断を持つ。退避エンティティは「元データを削除する」という特定条件下でのみ成立し、
既定が逆転する。同じfileへ並べると、どちらの既定が適用されるかを読者が取り違える。

`documentation_standards/README.md` は「1つの標準を説明するのに複数ファイルが要る場合は
ディレクトリ化してよい」と定めており、`naming/` に前例がある。

**結果:** 提案1を受諾。file名は `evacuation.md`

「一旦」とあるため暫定採用である。より適切な語が見つかった場合の改名を妨げない。

## 論点2: 一般則を今回の具体ケースへ適用する

### イテレーション0: `meals` の全項目を分類し、引き継ぎ範囲を確定する

#### 提案0

**推奨:** `comment` を引き継ぐ。あわせて確認ダイアログを廃止し、一覧へコメントを表示する。

##### `meals` の全項目の分類（`evacuation.md` の手順）

| `meals` の項目 | 扱い | 理由 |
| --- | --- | --- |
| `id` | 引き継がない | 行の識別子であり、元データの内容ではない。退避先は独自のidを持つ |
| `user_id` | 引き継ぐ | 実装済み |
| `dish_id` | 引き継ぐ | 実装済み |
| `meal_type` | 引き継ぐ | 実装済み |
| `date` | **落とす** | 日付が未決であることが延期の定義そのもの。意図をもって落とす唯一の項目 |
| `comment` | **引き継ぐ（今回の変更）** | 落とす理由を書けない |
| `created_at` / `updated_at` | 引き継がない | 行のライフサイクルmetadataであり、元データの内容ではない。退避先は自身の作成時刻を持つ |

未分類の項目はない。落とすと決めたのは `date` だけであり、それは延期の定義から導かれる。

##### 変更内容

- `postponed_meals` へ `comment` カラムを追加する。`meals.comment` と同じく `string` かつ nullable。
  コメントなしの食事が存在するため、NOT NULL にはできない
- `Meal::Postponed::Root` へ `attribute :comment, :string` と `validates :comment, presence: false` を追加する
- `postponeMeal` が元の食事の `comment` を引き継ぐ
- `schedulePostponedMeal` が `comment` を新しい `Meal` へ復元する

##### 確認ダイアログを廃止する

現在の文言は `この食事を延期しますか？（食事コメントは失われます）` である。

論点4でこのダイアログを置いた理由は「コメントを書いた食事を延期したときに黙って消えるほうが害が大きい」
だった。`comment` を引き継ぐと、この理由が成立しなくなる。

延期で失われるのは `date` だけになり、それはユーザーが意図的に捨てているものである。
残る全項目は `postponed_meals` に保存され、日付を与えれば復元される。既存の「他の日へ」も
日付を変えるが確認を求めていない。破壊性が同等以下になったため、確認を外す。

##### 一覧パネルへコメントを表示する

`ChoosePostponedMeal.tsx` は現在 `dishName` と `mealType` だけを表示している。
引き継いだコメントが見えないと、ユーザーは引き継がれたことを確認できない。

`MealCard` が食事コメントを小さめのイタリック体で表示しているのと同じ扱いで、料理名の下へ置く。
コメントがない行では行を伸ばさない。

##### 波及する作業

- 新規 migration が1本必要。**DB migration であるため、論点10（`task-design-discussion.md`）により
  完了時に commit・push の要否をユーザーへ確認する**
- `design.md` の要件・データモデル・操作フロー・caller contract の更新
- `tasklist.md` へ Phase 7 を追加
- 既存の RSpec / Jest のうち、コメントが失われることを前提にしたものがあれば書き換える

#### 提案背景

##### 一般則の適用として全項目を列挙した理由

論点1で合意した `evacuation.md` は「元データの全項目を一度列挙し、引き継ぐ／落とすを分類し、
未分類の欠落を失敗とする」と定める。`comment` だけを追加するのではなく、`meals` の全カラムを
分類したのはこのためである。

結果として、意図をもって落とすのは `date` だけであることが確認できた。論点2の当初設計では
`date` と `comment` の2つを落としていたが、`comment` の側に書ける理由がなかった。

##### 確認ダイアログの廃止を同じ論点へ含める理由

ダイアログの存在理由は「コメントが失われること」だけだった。`comment` を引き継ぐ決定と、
ダイアログの根拠が消えることは同一のdecisionから導かれる。別論点へ分けると、
根拠を失ったダイアログが残る状態を一度作ることになる。

## 論点5: 確定後に延期一覧が再取得されず、割り当てた行が消えない

> あれ、延期した食事を割り当てた後、フロントエンドの延期した食事一覧から割り当てたもの消えてなくない？

##### 事象と原因（実測）

`usePostponedMealMode.ts` の確定処理は次のとおり。

```js
onCompleted: () => {
  if (onDataChanged) onDataChanged();   // カレンダー（meals）だけを再取得
  setSelectedPostponedMeal(null);
  changeCalendarModeToDisplayCalendarMode();
},
```

`refetchPostponedMeals()` が呼ばれていない。`onDataChanged` はカレンダーの再取得であり、
延期一覧は別のquery（`postponedMeals`）である。server側では `postponed_meals` の行が削除されているが、
frontend の cache が古いまま残る。

`refetchPostponedMeals` は同じ hook 内で受け取っているのに使われておらず、書き忘れである。

##### 同種の抜けが延期側にもある

`MealCard/index.tsx` の延期処理も `onCompleted: () => { onChanged(); }` だけで、
`refetchPostponedMeals` を呼んでいない。一覧を開いていない状態からの操作のため症状は出にくいが、
「延期 → すぐ一覧を開く」で古い cache が出る可能性がある。

##### 修正範囲

**A を採る。** 確定側と延期側の両方で `refetchPostponedMeals` を呼び、あわせて
「確定後に一覧から消える」ことを検証する Jest を追加する。

## 論点6: DoD の各項目に対応する test があるかを、tasklist の自己レビューgateで検査する

**ステータス:** 決定

**種別:** 認識齟齬

### イテレーション0: gate へ検査項目を追加するか確定する

#### 提案0

**判断の対象:** `plugins/tumeda-dev/skills/task-design/tasklist-design.md` の自己レビューgateへ
1項目を追加する。

##### 追加する検査項目

```markdown
- [ ] **DoDの各項目に、それを担保するtaskがあるか**: DoDに書いた観測可能な結果が、
      testまたは確認taskのどれにも対応していない状態になっていないか。
  - DoDから順にたどり、各項目を担保するtaskを指させることを確認する。taskから逆にたどらない。
  - やってしまいがちな失敗: testの一覧を先に作り、DoDと突き合わせずに揃ったとみなす。
    DoDに書いたのにtestが無い項目は、実装者に「書かなくてよい」と読まれる
```

##### 既存gateとの違い

現行gateには既に次がある。

> - [ ] **各phaseにtest作成・変更があるか**: 実行だけでなく、変更挙動を担保するtestがあるか。

これは test が**存在するか**を問う。今回抜けたのは、test は存在したが **DoD の一項目に対応する test が
無かった**ことである。存在の有無では検出できない。

##### 今回の実例

`tasklist.md` Phase 4 の DoD は3項目ある。

1. 一覧から1件タップして日付をタップすると、時間帯を訊かれずに食事が登録される
2. 登録された食事の時間帯は延期した食事が持っていた値と一致し、食事コメントは空である
3. **確定した行は一覧から消え、同じ料理の他の行は残る**

これに対して Jest の項目は「確定パネルに時間帯選択UIが無いこと」「日付タップでmutationが呼ばれること」の
2つで、**3番目に対応するものが無い**。既存gateは「testがあるか」を問うため通過してしまう。

実装者はtaskに書かれた範囲を実装するため、DoDに書いてもtaskに落ちていない項目は実装されない。
今回の不具合はこの経路で生じた。

#### 提案背景

##### 原因ownerをskillと判定した根拠

論点5は「成果物固有」に見える。designもDoDも正しく、実装だけが外れていたためである。
しかし実装が外れた理由をたどると、tasklistのtest項目がDoDから導かれていなかった。

DoDとtaskの対応を検査する仕組みが無いため、DoDに書いた項目が静かに落ちる。
これはrepositoryを問わず再発する構造であり、原因ownerはskillである。

##### 既存gateを置き換えるのではなく足す理由

「testがあるか」と「DoDの各項目に対応があるか」は別の検査である。前者はtestの不在、
後者は網羅の欠落を見る。片方が通っても他方は通らないため、置き換えず並べる。

#### 提案0へのフィードバック

**結果:** 提案0を受諾

> ok

### 決定

`plugins/tumeda-dev/skills/task-design/tasklist-design.md` の自己レビューgateへ、次の1項目を追加する。

```markdown

      testまたは確認taskのどれにも対応していない状態になっていないか。
  - DoDから順にたどり、各項目を担保するtaskを指させることを確認する。taskから逆にたどらない。
  - やってしまいがちな失敗: testの一覧を先に作り、DoDと突き合わせずに揃ったとみなす。
    DoDに書いたのにtestが無い項目は、実装者に「書かなくてよい」と読まれる
```

既存の「各phaseにtest作成・変更があるか」は置き換えず並べる。前者はtestの不在、後者は網羅の欠落を見る
別の検査であり、片方が通っても他方は通らない。

**根拠となった実例:** `tasklist.md` Phase 4 の DoD 3項目のうち、3番目「確定した行は一覧から消え、
同じ料理の他の行は残る」に対応する Jest が存在しなかった。Jest は2つ存在したため既存gateは通過した。
実装者はtaskに書かれた範囲を実装するため、DoDに書いてもtaskに落ちていない項目は実装されず、
論点5の不具合が生じた。

## 論点7: 修正で `Store reset while query was in flight` を作り込んだ

**ステータス:** 決定

**種別:** 認識齟齬

### イテレーション0: 原因と再発防止先を確定する

#### 提案0 / 決定

##### 起点となったfeedback

論点5の修正を適用した後、ユーザーの動作確認で報告された。

> Uncaught (in promise) Invariant Violation: Store reset while query was in flight (not completed in link chain)
> at QueryManager.clearStore (QueryManager.ts:878:5) at ApolloClient.ts:674:6 at async refreshData
> 延期したものの再配置は成功したけどエラー出た

##### 原因（実測）

論点5の修正で次のように書いた。

```js
onCompleted: async () => {
  if (onDataChanged) onDataChanged();   // awaitしていない
  await refetchPostponedMeals();
  ...
}
```

`onDataChanged` の実体は `useRefreshCalendarData.tsx` の `refreshData` であり、次を行う。

```js
await apolloClient.clearStore();   // Apolloのキャッシュを全消去
refetchMealsForCalendar();
```

`onDataChanged()` を待たずに `refetchPostponedMeals()` を始めたため、in flight のqueryが
store resetと衝突した。**論点5の修正そのものが作り込んだ不具合である。**

##### 適用した修正

`onDataChanged` を `await` してから再取得する。

```js
// onDataChanged（refreshData）は apolloClient.clearStore を含む。
// 完了を待たずに再取得を始めると、in flightのqueryがstore resetと衝突して
// "Store reset while query was in flight" になる。必ず待つ。
if (onDataChanged) await onDataChanged();
await refetchPostponedMeals();
```

##### 実機での検証結果

`visual-inspector` で実操作し、次を観測した（推測ではない）。

- console 8件はすべて React DevTools / HMR / Fast Refresh / Apollo DevTools の通常ログ。
  `[error]` 0件、`Invariant Violation` 0件、`Store reset while query was in flight` 0件、`pageerror` 0件
- 確定した行（`row-15` ほうれん草のナムル）が一覧から消え、残り9行は確定前と一致
- 8/29のカレンダーへ当該食事が登録された

ユーザーの動作確認でも「ok治ってたわ」と確認済み。

##### 未検証として残る範囲

- 「同じ料理の他の行が残る」ケースは実機未再現（対象が1行しかなかったため）。Jestでは検証済み
- 「延期直後に一覧を開く」経路は実機未確認
- **修正前にproductionでなぜ古い一覧が出ていたかは未解明。**`refreshData` が `clearStore` を含む以上、
  キャッシュは消えるはずであり、「refetchが呼ばれていないから古い」という論点5の原因診断は
  productionでは成立しない可能性がある。修正後に正しく動くことは実測したが、
  元の不具合の完全な説明はできていない

### 根本原因と再発防止

**共有されていなかった知識:** `onDataChanged` という名前が、Apolloのキャッシュ全消去（`clearStore`）を
含む破壊的な操作であることを示していない。呼び出し側は「データが変わったことを通知する軽い関数」と読む。

**codeを読めば分かるか:** 分かる。`useRefreshCalendarData.tsx` を開けば `await apolloClient.clearStore()` が
2行目にある。私はそれを読まずに、自分の非同期処理と並走させた。

**どこに書けば次回この議論が不要になるか:** `onDataChanged` / `refreshData` の実体が全キャッシュ消去で
あることを、カレンダー配下のdocsまたは当該fileの近傍へ記録する。次にこのcallbackへ処理を足す者が、
実装を開かずに「これは待つ必要がある」と判断できる状態にする。

この知識はこのrepositoryの実装に固有であり、他のrepositoryでは成立しない。
したがって `development_standard/README.md` の判断（他のリポジトリでも成立するならplugin側）に照らすと、
利用先へ置く。plugin側の標準にはしない。

**具体的な記録先の提案は doc-enricher で扱う。**
