# 議論記録

## 論点1: 保留されるドメインオブジェクトの実体は何か

**ステータス:** 分解済み

**種別:** TBDヒアリング

### イテレーション0: 保留プールが保持する実体と、元の食事記録の扱いを確定する

#### 提案0

**推奨:** b。`Meal` の定義そのものが a と c を排除し、b だけがご依頼の「保存」「欲しいものリスト」の性格まで無理なく収容できるためです。

##### a. `meals.date` を nullable にし、日付未定の `Meal` を保留状態とみなす

保留 = `date IS NULL` の `Meal`。既存の `Meal` レコードをそのまま使い回し、日付を外すことで保留、日付を入れ直すことで吐き出しとする。

| 操作 | `meals` の行 |
| --- | --- |
| 保留する | `date` を `NULL` へ。`dish_id` / `meal_type` / `comment` は保持 |
| 吐き出す | `date` に新しい日付を入れる |

カレンダークエリ側は `date IS NOT NULL` の絞り込みが全箇所に必要になる。

##### b. 保留エントリを別エンティティとして新設し、料理への参照を持つ。保留時に元の `Meal` は削除する

保留 = 「この料理をいつか食べたいが、日付は決めていない」という意思を表す独立したレコード。日付・時間帯を持たない（それらは未決だからこそ保留されている）。

| 操作 | `meals` の行 | 保留エントリの行 |
| --- | --- | --- |
| 保留する | 削除される | `user_id` + `dish_id` で新規作成 |
| 吐き出す | 指定日・指定時間帯で新規作成 | 削除される |
| 食事を経由せず直接入れる | 変化なし | `user_id` + `dish_id` で新規作成 |

最終行が示すとおり、この案だけは `Meal` を起点にしない投入経路を追加コストなしで持てる。

##### c. `Meal` を残したまま保留状態を表すカラム（フラグ等）を持たせる

保留 = `meals` に `is_pending` 等を追加した状態。行はそのまま残り、カレンダー表示から除外される。

`date` / `meal_type` は「食べられなかった日」の値を保持し続ける。

#### 提案背景

##### この提案が満たす必要のある条件

ご依頼から、保留プールが満たすべき性格は二つ読み取れます。

1. **待避**: 「1度食事登録したんだけど、突然の予定とかでその料理が食べられなかったときに保留しておいて、将来的に食事に割り当てる」
2. **保存 / ストック**: 「保存の意味もある」「Amazonの欲しいものリストみたいに」「蒲田で行きたい場所」

2つ目が効きます。「行きたい場所」は *食事登録を経ていない* 対象です。つまり保留プールの中身は「元・食事」だけとは限りません。実体の選択肢は、`Meal` を経由しない投入を将来自然に受け入れられる必要があります。

##### 推奨理由

**`Meal` の定義が a と c を排除します。**

`backend/app/domain/business/food/README.md` は `Meal` を「**ある日に、ある料理を食べた記録**」と定義し、`dish_id` の nullable 化を明示的に禁じています。この定義に照らすと、*食べられなかった* 食事の行が `meals` に残り続けること自体が定義違反です。

- a: `date` が `NULL` の `Meal` は「日付のない、ある日の記録」であり、語義矛盾を起こします
- c: `is_pending = true` の `Meal` は「食べていない、食べた記録」であり、同じ矛盾を別の形で持ちます

さらに architecture doc のフィールド追加判断——「このエンティティはこのフィールドなしで完結した意味を持つか？ → Yes なら nullable 追加ではなく別エンティティへ切り出す」——にも a と c は反します。`Meal` は `date` を必須として完結した意味を持っているためです。

**削除は情報の喪失ではありません。**

b の「元の `Meal` を削除する」に抵抗を感じる余地はありますが、`Meal` が「食べた記録」である以上、食べなかった食事の行は *事実として誤り* です。削除は履歴を失う操作ではなく、誤った記録を正す操作にあたります。残すべきは「その料理を食べたい」という意思だけで、それを担うのが保留エントリです。

**同型の前例が既にあります。**

本 repository は「日付は決まっているが料理が未決定」を `Meal` の nullable カラムではなく `MealFrameEntry` という別モデルで表現しました。今回はその鏡像（料理は決まっているが日付が未決定）にあたり、同じ判断を適用すると b になります。

##### この提案で決めないこと

以下は b を採った場合に続けて決める下位の判断であり、この論点には含めません。

- 保留エントリが `dish_id` 以外に何を持つか（元の日付・時間帯・食事コメントを引き継ぐか、メモや並び順を持つか）
- 保留プールへの入口をどこに置くか、吐き出しの操作をどう作るか
- ドメイン名（「保留枠」の「枠」は `Meal::Frame` と衝突するため、そのままは使えません）とモジュール配置
- 将来の複数箱への拡張余地をどこまで今回の構造へ織り込むか

#### 提案0へのフィードバック

**結果:** b を採用

> b

案bをそのまま受諾。a・cの排除理由、元の`Meal`削除の是非、`Meal`を経由しない投入経路の必要性のいずれにも異議なし。

### 決定

延期された食事は、`Meal` とは別の新しいエンティティ `Business::Food::Meal::Postponed::Root`（テーブル `postponed_meals`）とする。料理への参照を持ち、日付は保持しない。

<!-- 語彙は論点3の決定に同期。当時は「保留プールのエントリ」と呼び、時間帯も持たない案だった。時間帯を持つ判断は論点2、名称は論点3が典拠。 -->

食事を延期したとき、元の `meals` の行は削除する。`Meal` は「ある日に、ある料理を食べた記録」であり、食べなかった食事の行を残すことは事実として誤りであるため、削除は履歴の喪失ではなく誤った記録の訂正にあたる。

延期された食事は `Meal` の行の存在を前提としない構造を持つ。ただし「蒲田で行きたい場所」のような一度も日付が決まっていない対象を同じテーブルへ入れることは、論点3の決定により行わない。その用途は将来の移行で扱う。

**排除した案と理由:**

- `meals.date` を nullable にする案: `date` が `NULL` の `Meal` は「日付のない、ある日の記録」となり、`Meal` の定義と語義矛盾を起こす。`Meal` を経由しない投入経路も持てない
- `Meal` に保留フラグを持たせる案: `is_pending = true` の `Meal` は「食べていない、食べた記録」となり、同じ矛盾を別の形で持つ。architecture doc のフィールド追加判断（完結した意味を持つエンティティへ nullable を足さない）にも反する

## 論点2: 保留エントリが保持する情報と、同じ料理の重複の扱い

**ステータス:** 決定

**親論点:** 論点1

**種別:** TBDヒアリング

### イテレーション0: 保留エントリのデータ表現を確定する

#### 提案0

**推奨:** 料理への参照だけを持つ最小構成とし、同じ料理は保留プール内で1件に限る。

##### 保持する情報

| 候補 | 採否 | 理由 |
| --- | --- | --- |
| `user_id` | **持つ** | ユーザー別のプールであるため。既存の全エンティティと同じ |
| `dish_id` | **持つ** | 論点1で決定済み。保留の対象そのもの |
| 元の食事の `date` | 持たない | 日付が未決であることが保留の定義。かつ食事を経由しない投入では値が存在せず nullable になる |
| 元の食事の `meal_type`（朝/昼/夜） | 持たない | 同上。食事を経由しない投入では値が存在しない |
| 元の食事の `comment` | 持たない | 食事コメントは「その日のその食事について」の記述であり、日付を外した保留エントリへ移すと意味が変わる |
| 保留に固有のメモ | 持たない | 保留エントリはメモなしで完結した意味を持つ。必要になった時点で追加する |
| 並び順（`position`） | 持たない | `created_at` の降順で「最近保留したものが上」を表現できる。手動並び替えの要求が出た時点で追加する |

結果として、保留エントリのテーブルは次の形になります（テーブル名・カラム名はドメイン名の確定待ち）。

```text
{保留エントリ}
  id
  user_id      NOT NULL
  dish_id      NOT NULL
  created_at   NOT NULL
  updated_at   NOT NULL
  UNIQUE (user_id, dish_id)
```

##### 同じ料理の重複

`UNIQUE (user_id, dish_id)` を張り、**同じ料理は保留プール内に1件までとする。**

したがって次の挙動になります。

| 状況 | 結果 |
| --- | --- |
| 同じ料理を2日分登録し、両方とも食べられず保留した | 保留エントリは1件。2回目の保留は既存エントリを見つけて何もしない（エラーにしない） |
| 保留中の料理を吐き出した後、また食べられず保留した | 再び1件作られる |

#### 提案背景

##### この提案が満たす必要のある条件

論点1で「保留エントリは『この料理をいつか食べたいが、日付は決めていない』という意思を表す」と決めた。この定義を、実際に保存される値として破綻なく表現する必要がある。

判断には architecture doc のフィールド追加基準を使った。

> 「このエンティティはこのフィールドなしで完結した意味を持つか？」→ Yes ならフィールドを追加せず、そのフィールドが必要になる文脈を別エンティティとして切り出す

##### 元の食事の文脈を引き継がない理由

`date` と `meal_type` については、上の基準に加えてもう一つ決定的な事情がある。論点1で「保留エントリは `Meal` の存在を前提としない」と決めたため、食事を経由しない投入経路では、これらの値が**そもそも存在しない**。持たせれば nullable になり、architecture doc が禁じる「独立して存在できるエンティティへの nullable 追加」に該当する。

さらに `NULL` の意味も曖昧になる。`meal_type` が `NULL` のとき、「食事を経由せず入れたので不明」なのか「朝昼夜どれでもよい」なのかを区別できない。

##### 重複を1件に絞る理由

「Amazonの欲しいものリスト」という説明が判断の手がかりになる。欲しいものリストは同じ商品を2行持たない。保留プールも「この料理を食べたい」という意思の集合であり、意思は同じ料理について2つ存在しない。

重複を許すと、一覧に同じ料理名が並び、どちらを吐き出すかという意味のない選択がユーザーへ発生する。

##### この提案で決めないこと

- ドメイン名とテーブル名（次の論点で扱う）
- 保留プールへの入口と吐き出しの操作
- 将来の複数箱への拡張余地

#### 提案0へのフィードバック

**結果:** 2点とも修正要求。うち `meal_type` は概念定義の誤りに遡る

> 重複はしていいわ。2回食べようと思っていたのが保留になることもある。そして、meal_typeについては「夜用に考えていた料理なのだから、吐き出すときも夜に置きたい」が認識に近い。assign-dishは別に元々入れてたものが無い。元々夜食べたいと思っていたものは基本的には夜食べたいことが多いし、そもそも朝昼晩を選ぶのが面倒くさい

- **重複**: 「同じ料理について意思は2つ存在しない」という提案0の前提が誤り。同じ料理を2回食べる意図があり、その両方が保留になる事象が実在する。`UNIQUE (user_id, dish_id)` は不成立
- **`meal_type`**: 提案0は「保留エントリが覚えておくべきことではなく、吐き出すときに選ぶこと」と整理し、その根拠に「assign-dish も時間帯を選ばせている」を挙げたが、この類推が誤り。assign-dish には引き継ぐべき事前の文脈が存在しないのに対し、保留は元の食事という文脈を持つ。持っている情報を捨てて選び直させるのは操作の後退にあたる

このfeedbackは提案0のフィールド選択だけでなく、論点1で置いた保留エントリの概念定義（「この料理をいつか食べたい」）自体を、時間帯を含む定義へ更新する必要を示している。

### イテレーション1: 保留エントリを「料理 + 時間帯」の意思として定義し直す

#### 提案1

##### 保留エントリの概念定義（更新）

保留エントリは「**この料理を、この時間帯に、いつか食べたい**」という意思を表す。未決なのは日付だけである。

##### 保持する情報

| 候補 | 採否 | 理由 |
| --- | --- | --- |
| `user_id` | **持つ** | ユーザー別のプールであるため |
| `dish_id` | **持つ** | 保留の対象そのもの |
| `meal_type`（朝/昼/夜） | **持つ・NOT NULL** | 更新後の概念定義に含まれる。元の食事から引き継ぎ、吐き出し時の既定値として使う |
| 元の食事の `date` | 持たない | 日付が未決であることが保留の定義そのもの |
| 元の食事の `comment` | 持たない | 食事コメントは「その日その回の食事について」の記述であり、日付を外すと対象を失う。時間帯と違い、次に食べるときへ引き継ぐ意味を持たない |
| 保留に固有のメモ | 持たない | メモなしで完結した意味を持つ。必要になった時点で追加する |
| 並び順（`position`） | 持たない | `created_at` の降順で「最近保留したものが上」を表現できる |

```text
{保留エントリ}
  id
  user_id      NOT NULL
  dish_id      NOT NULL
  meal_type    NOT NULL
  created_at   NOT NULL
  updated_at   NOT NULL
```

一意制約は張らない。

##### 同じ料理の重複

**重複を許す。** 保留するたびに新しい行が1件作られる。

| 状況 | 結果 |
| --- | --- |
| 同じ料理を2日分（どちらも夜）登録し、両方とも食べられず保留した | 保留エントリは2件。「2回食べたい」という意思がそのまま2件で表現される |
| 同じ料理を昼と夜で登録し、両方保留した | 保留エントリは2件（`meal_type` が異なる） |
| 1件を吐き出した | 残り1件。もう一方の意思は保持される |

##### 吐き出し時の時間帯

保留エントリの `meal_type` を既定値として使い、**時間帯の選択を求めない**。日付の指定だけで食事登録が完了する。

#### 提案背景

##### 診断の遡り先

提案0は `meal_type` を「吐き出すときに選ぶこと」と整理した。feedbackはこの整理を否定し、その根拠として「assign-dish には元々入れてたものが無い」を示した。

この指摘は提案0のフィールド選択の誤りにとどまらない。提案0は保留エントリの意思を「この料理を食べたい」と読んでいたが、実際に保留されている意思は「この料理を、この時間帯に食べたい」である。したがって `meal_type` は完結したエンティティへの追加フィールドではなく、**エンティティの定義に含まれる属性**である。提案1は概念定義の更新を先に置き、フィールド構成をそこから導いた。

この更新により、提案0が `meal_type` の排除根拠にしていた architecture doc のフィールド追加基準（「このフィールドなしで完結した意味を持つか」）は、`meal_type` に対しては適用対象外になる。`date`・`comment`・メモ・並び順に対しては引き続き有効であり、提案0の判断を維持する。

##### `meal_type` を nullable にしない理由

提案0は「食事を経由しない投入では `meal_type` が存在しない」ことを nullable 化の懸念として挙げた。今回のscopeでは投入経路が「食事から保留する」だけであり、`Meal.meal_type` は `NOT NULL` であるため、保留エントリの `meal_type` も `NOT NULL` を満たせる。

将来、食事を経由せず直接投入する経路を追加するときは、その経路が `meal_type` を供給する必要がある。これは今回の選択が受け入れる帰結であり、その機能を設計する時点で改めて判断する。先回りして nullable にすると、値が存在する現在の全エントリまで「未指定かもしれない」扱いになり、吐き出し時に既定値を使えなくなる。

##### 重複を許す構造

数量カラムではなく行の複数化で表現する。2件の保留は別々の日へ吐き出され、片方だけを取り消すこともあるため、独立して消滅できる単位である必要がある。

##### 既存モデルとの対称性

更新後の定義は既存の `MealFrameEntry` と鏡像をなす。

| | 決まっているもの | 未決のもの |
| --- | --- | --- |
| `MealFrameEntry` | 日付 + 時間帯 + 枠 | 料理 |
| 保留エントリ | 料理 + 時間帯 | 日付 |

`Meal` は3つすべてが決まった状態であり、2つの未決モデルがそれぞれ異なる軸を空けている構造になる。

#### 提案1へのフィードバック

**結果:** `meal_type` を nullable にする方向の指摘。提案1が挙げた NOT NULL の理由は成立しない

> 確かにその意味だとNOT NULLじゃなくていいわ

提案1は NOT NULL の理由として「先回りして nullable にすると、値が存在する現在の全エントリまで『未指定かもしれない』扱いになり、吐き出し時に既定値を使えなくなる」を挙げたが、これは誤り。値の有無を実行時に判定すれば、値があるエントリでは既定値を使い、ないエントリでだけ選択を求めればよく、既定値が使えなくなる事態は生じない。

提案0で挙げた「NULL の意味が『不明』か『どれでもよい』か曖昧になる」も、更新後の概念定義では成立しない。NULL の発生経路は「時間帯を指定せずに投入した」の一つだけであり、意味は「時間帯の希望なし」に定まる。「不明」と「どれでもよい」は、吐き出し時に選択を求めるという同一の扱いへ収束する。

提案1の NOT NULL 判断を支える理由は残っていないため、別の理由が立つかを提案2で検討する。

### イテレーション2: nullable と NOT NULL を、将来の変更コストの非対称性で判定し直す

#### 提案2

`meal_type` を **NOT NULL** のまま採用する。ただし理由は提案1のものを撤回し、次へ置き換える。

##### 判断根拠: 制約を緩める migration は安く、締める migration は高い

| 今回の選択 | 将来「時間帯なしの投入」を追加するときに必要な作業 |
| --- | --- |
| NOT NULL | `change_column_null` で nullable へ緩める。既存行は全て値を持つため backfill 不要。非破壊 |
| nullable | 変更不要 |

逆方向は成立しない。nullable で始めて後から NOT NULL へ締めるには、値のない既存行をどう埋めるかの判断と backfill が要る。

つまり NOT NULL を選んでも将来の柔軟性は失われない。緩める側の migration が安いためである。

##### 判断根拠: 今日到達できない分岐を作らない

今回のscopeで保留エントリを作る経路は「食事から保留する」だけであり、`Meal.meal_type` は `NOT NULL` である。したがって `meal_type` が存在しない保留エントリは**今日ひとつも作れない**。

nullable にすると、吐き出し処理と一覧表示に「時間帯がない場合」の分岐が生まれるが、その分岐は今日到達不能であり、テストで通ることも確認できない。実際にその経路を追加する時点で、動作を確認しながら分岐を作るほうが安全である。

##### この判断が受け入れる帰結

将来「食事を経由せず料理を直接プールへ入れる」経路を作るとき、`meal_type` を nullable へ緩める migration が1本必要になる。それが唯一のコストである。

#### 提案2へのフィードバック

**結果:** 提案2を受諾。NOT NULL で確定

migrationの非対称性（緩める側は非破壊、締める側は backfill が要る）と、到達不能な分岐を作らない方針を受け入れ、NOT NULL を採用。

### 決定

**概念定義:** 「この料理を、この時間帯に、いつか食べたい」という意思を表す。未決なのは日付だけである。

**保持する情報:**

```text
postponed_meals
  id
  user_id      NOT NULL
  dish_id      NOT NULL
  meal_type    NOT NULL
  created_at   NOT NULL
  updated_at   NOT NULL
```

一意制約は張らない。

<!-- テーブル名は論点3の決定に同期。この論点の時点では「保留エントリ」と呼び、名称は未確定だった。 -->

**持たせないものと理由:**

- 元の食事の `date`: 日付が未決であることが保留の定義そのもの
- 元の食事の `comment`: 「その日その回の食事について」の記述であり、日付を外すと対象を失う。次に食べるときへ引き継ぐ意味を持たない
- 保留に固有のメモ: メモなしで完結した意味を持つ。必要になった時点で追加する
- 並び順（`position`）: `created_at` の降順で「最近保留したものが上」を表現できる。手動並び替えの要求が出た時点で追加する

**重複:** 許す。保留するたびに新しい行が1件作られる。同じ料理を2日分（どちらも夜）保留すれば2件になり、「2回食べたい」という意思が2件で表現される。片方を吐き出しても、もう一方は残る。数量カラムではなく行の複数化で表現するのは、2件が別々の日へ吐き出され、片方だけ取り消されることもあるため、独立して消滅できる単位である必要があるため。

**`meal_type` の扱い:** 元の食事から引き継ぎ、吐き出し時の既定値として使う。吐き出し時に時間帯の選択を求めない。

`meal_type` を `NOT NULL` にするのは、今回のscopeで保留エントリを作る経路が「食事から保留する」だけであり、`Meal.meal_type` が `NOT NULL` であるため、値のない保留エントリを今日ひとつも作れないことによる。nullable にすると到達不能な分岐が吐き出し処理と一覧表示に生まれ、テストで通ることも確認できない。将来「食事を経由せず直接投入する」経路を追加するときは、`change_column_null` で nullable へ緩める migration が1本必要になる。既存行は全て値を持つため backfill は不要であり、この方向の migration は非破壊である。逆に nullable で始めて後から締める migration は backfill の判断を伴うため高い。この非対称性により、NOT NULL を選んでも将来の柔軟性は失われない。

**既存モデルとの対称性:**

| | 決まっているもの | 未決のもの |
| --- | --- | --- |
| `MealFrameEntry` | 日付 + 時間帯 + 枠 | 料理 |
| `PostponedMeal` | 料理 + 時間帯 | 日付 |

`Meal` は3つすべてが決まった状態であり、2つの未決モデルがそれぞれ異なる軸を空けている。

**a. Hold（保留）**

**b. Candidate（食事候補）**

**c. Pool::Entry（保留プール / 保留エントリ）**

#### 提案背景

##### この提案が満たす必要のある条件

依頼文の「保留枠」はそのまま使えない。「枠」は `Meal::Frame`（「パスタ」「魚料理」等の再利用可能な枠マスタ）として既にユビキタス言語に確立しており、無関係な概念へ同じ語を当てると認識ズレが恒久化する。したがって「枠」を外した名前を決める必要がある。

また `CLAUDE.md` は命名を合意が要る設計判断として扱っており、テーブル名とクラス名は変更コストが高く長期間存在する。

##### 「保留」という日本語自体は衝突していない

衝突しているのは「枠」だけである。「保留」は既存のユビキタス言語のどれとも競合しない。したがって日本語側で「保留」を採ることは、それ自体としては問題を起こさない。

##### 進化例を根拠にしない

architecture doc は「進化例は検証に使うのであって命名の根拠にしてはならない。特定の進化例に特化した命名は、現状のオペレーションをないがしろにする」と定めている。

したがって「将来ウィッシュリストになるから `Candidate`」「将来箱が増えるから `Pool`」という理由付けは採らない。現状のオペレーションは「食べられなかった料理を、日付未定のまま取っておき、後で日付を決めて食べる」であり、進化テストは各案がそこで破綻しないことの確認にのみ使った。

##### 推奨理由

ユビキタス言語の目的は、ドメイン専門家と実装が同じ語で話せることにある。本 repository のドメイン専門家は依頼者であり、その語彙は「保留」である。b の `Candidate` は「行が何であるか」をより正確に名指す利点を持つが、その利点と引き換えに、会話とコードの間へ恒久的な翻訳を持ち込む。

c は将来の拡張が構造的に自然だが、箱の実体がない階層を先に作ることになり、かつ依頼文自身が箱を別概念として扱う可能性を残している。現時点で確定していない構造を名前空間へ固定する判断は早い。

### イテレーション3: 「延期」の品詞と、meal / dish の帰属を確定する

#### 提案3

##### これは meal である

延期されたのは料理ではなく、その料理を食べる機会である。

`Dish`（料理マスタ）は延期されない。「カレー」という料理そのものは、食事が中止されても何ら変化せず、マスタに存在し続ける。中止によって失われたのは「その日にそれを食べる」という機会であり、それは食事（`Meal`）の側にある。

保持する属性からも同じ結論になる。論点2で確定したとおり、このエンティティは `meal_type`（朝食 / 昼食 / 夕食）を必須属性として持つ。これは食事の時間帯であり、料理マスタには存在しない概念である。dish 側の概念だとすると `meal_type` を持つ理由が説明できない。

論点2で確認した既存モデルとの対称性も、meal 側であることを支持する。

| | 決まっているもの | 未決のもの |
| --- | --- | --- |
| `Meal` | 日付 + 時間帯 + 料理 | なし |
| `MealFrameEntry` | 日付 + 時間帯 + 枠 | 料理 |
| **延期された食事** | **時間帯 + 料理** | **日付** |

3つはいずれも食事という同じ軸の上にあり、どの要素が未決かだけが異なる。dish 側の概念であれば、この並びに入らない。

##### 品詞は形容詞形を採る

形容詞形での運用は可能である。ただし ActiveRecord モデル名の導出規則から外れる。

| | 日本語 | ドメインクラス | ARモデル | テーブル | 規約 |
| --- | --- | --- | --- | --- | --- |
| **名詞形** | 延期 | `Business::Food::Meal::Postponement::Root` | `MealPostponement` | `meal_postponements` | 導出どおり |
| **形容詞形（推奨）** | 延期された食事 | `Business::Food::Meal::Postponed::Root` | `PostponedMeal` | `postponed_meals` | **語順が反転する** |

形容詞形を推す理由は、行が表しているものが行為ではなく物であるためである。

- `meal_postponements`（食事の延期）は延期という**出来事**の集合を指す。1行が1回の延期操作を表す読み方になる
- `postponed_meals`（延期された食事）は延期された**食事**の集合を指す。1行が1件の食事を表す

実際に保存されるのは「料理 + 時間帯を持ち、日付だけが未決の食事」であり、出来事ではなく物である。論点2で確定した概念定義「この料理を、この時間帯に、いつか食べたい」も物を指している。

##### 形容詞形が支払うコスト

`Postponed` は形容詞であるため、ドメインpathをそのまま平坦化すると `MealPostponed` → `meal_postponeds` となり英語として成立しない。成立させるには語順を反転して `PostponedMeal` → `postponed_meals` とする必要がある。

既存4テーブルはいずれも平坦化した語順を保っている。

| ドメインクラス | ARモデル | テーブル |
| --- | --- | --- |
| `Business::Food::Meal::Frame::Root` | `MealFrame` | `meal_frames` |
| `Business::Food::Meal::Frame::Entry::Root` | `MealFrameEntry` | `meal_frame_entries` |
| `Business::Food::Meal::Frame::Pattern::Root` | `MealFramePattern` | `meal_frame_patterns` |
| `Business::Food::Meal::Frame::Pattern::Entry::Root` | `MealFramePatternEntry` | `meal_frame_pattern_entries` |

`PostponedMeal` はこの並びで唯一、語順が反転したモデルになる。コストはこの一点であり、ドメイン側の名前空間 `Business::Food::Meal::Postponed::Root` は `Meal` 配下という帰属を保つため、論点3で合意済みのモジュール配置は変わらない。

#### 提案背景

##### この提案が満たす必要のある条件

feedback は e の採用を決めたうえで、2つの内部形式を問うた。品詞（名詞 / 形容詞）と、概念の帰属（meal / dish）である。

このうち帰属を先に確定する必要がある。形容詞形のテーブル名は `postponed_meals` か `postponed_dishes` かに分かれ、帰属が決まらなければ品詞の選択肢を具体化できないためである。提案3は帰属を先に置き、その上で品詞を扱う。

##### 帰属の判定に使った基準

「何が延期されたか」を問うた。`Dish` は料理マスタであり、食事の中止によって変化しない。変化したのは食事の側である。

補強として、論点2で確定済みの `meal_type` 必須という属性構成を使った。属性は概念の帰属を示す証拠であり、`meal_type` は料理マスタに存在しない概念であるため、dish 側の帰属では説明がつかない。

##### 品詞の判定に使った基準

「行が表すのは出来事か物か」を問うた。名詞形 `Postponement` は延期という出来事、形容詞形 `Postponed` は延期された食事という物を指す。論点2の概念定義が物を指しているため、形容詞形が実態に合う。

規約からの逸脱は品詞選択の帰結として発生するが、逸脱するのはARモデル名の語順1点のみであり、ドメイン側の名前空間と帰属には影響しない。

### 決定

**日本語のユビキタス言語:** 「延期」「延期された食事」。UI・会話・設計文書でこの語を使う。依頼文の「保留枠」は採らない。「枠」が `Meal::Frame`（再利用可能な枠マスタ）として既にユビキタス言語に確立しており、無関係な概念へ同じ語を当てると認識ズレが恒久化するため。

**帰属:** meal。延期されたのは料理ではなく、その料理を食べる機会である。`Dish`（料理マスタ）は食事の中止によって変化しない。論点2で確定した `meal_type` 必須という属性構成も、料理マスタに存在しない概念であるため meal 帰属を支持する。

**名前空間とテーブル:**

| | 名前 |
| --- | --- |
| ドメインクラス | `Business::Food::Meal::Postponed::Root` |
| ActiveRecordモデル | `PostponedMeal` |
| テーブル | `postponed_meals` |

`Business::Food::Meal::` 配下へ置くのは、architecture doc の帰属基準「既存のドメイン概念の文脈を外れても意味を持つか？」に対する答えが No であるため。`meal_type` は `Meal` の文脈でしか意味を持たず、このエンティティは `Meal` から生まれ `Meal` へ戻る。`Meal::Frame::` 配下には置かない。枠を参照せず、枠なしで意味を持つため。

**品詞:** 形容詞形。行が表すのは延期という出来事ではなく、延期された食事という物であるため。名詞形 `meal_postponements` は1行が1回の延期操作を表す読み方になり、論点2で確定した概念定義（「この料理を、この時間帯に、いつか食べたい」＝物）と合わない。

**受け入れた規約からの逸脱:** `PostponedMeal` は既存4テーブル（`meal_frames` / `meal_frame_entries` / `meal_frame_patterns` / `meal_frame_pattern_entries`）が守るドメインpath平坦化の語順から反転する唯一のモデルになる。`Postponed` が形容詞であるため、平坦化すると `meal_postponeds` となり英語として成立しないことによる。逸脱はARモデル名の語順1点のみで、ドメイン側の名前空間と帰属には影響しない。

**排除した案と理由:**

- **保留 / `Hold` / `Pending`**: 現状のオペレーション（食べられなかった料理を日付未定で取っておく）に対して「延期」より意味が広い。広い語で始めると、目的の異なるデータが同じテーブルへ混入する余地を先に作ることになる
- **食事候補 / `Candidate`**: 同上に加え、ユーザーの語彙と一致しない
- **保留プール / `Pool::Entry`**: 箱の実体がない階層を先に作ることになる
- **名詞形 `Postponement`**: 出来事を名指すため、物である実態と合わない

**「蒲田で行きたい場所」のような、一度も日付が決まっていない対象について:**

「延期」ではこの用途を括れない。これは認識したうえで受け入れた制約である。判断根拠は、言及されている用途と確定している用途は別であり、確定していない用途まで覆う語を選ぶことは現在の実態より広い抽象を先に置くことにあたる、というものである。将来この用途を運用するときは、コストを払って移行する。目的が絞られたデータの持ち方のほうが、移行時点で不適合なデータの混入を防げる。

害が大きい。コメントの有無で出し分ける案は、同じ操作の挙動が状況で変わりユーザーが予測できなくなるため
採らない。

**(3) 戻す操作:** ヘッダー右のケバブメニュー（`calendarMenu`）へ「延期した食事」を追加する。
実測では既に「食事割当て」「料理検索」「食事枠管理」「食事枠パターン管理」が並んでおり、
カレンダー上のモードを開始する入口として同じ位置が一貫する。

フローは既存の assign-dish と同じ2段階にする。

1. ケバブメニューを開き「延期した食事」をタップする
2. 画面下部に固定パネルが出る。実測した「食事登録」パネル（高さ401px = viewport の約47%、
   ヘッダーにタイトル + `×`）と同じ型を使い、中身を延期された食事の一覧にする
3. 一覧から1件をタップして選ぶ
4. パネルが帯状の確定パネル（案内文 + `^` + `×`）へ切り替わり、「食事を登録したい日を選んでください」と
   料理名を表示する
5. 日付カードをタップする
6. `Meal` が作られ、対応する `postponed_meals` の行が削除される
7. カレンダーが再取得され、その日に食事が現れる

**時間帯を選ばせない。** 論点2の決定により、延期された食事が持つ `meal_type` をそのまま使う。
実測した「食事登録」パネルには時間帯ラジオ（朝食 / 昼食 / 夕食）があるが、延期一覧パネルには置かない。

既存フローへ寄せるのは、依頼文が「assign-dishみたいに、保存したのを後で吐き出す」と述べており、
実測の結果 assign-dish が「一覧パネルで選ぶ → 帯状パネルへ切り替わる → 日付タップ」の2段階で
そのまま使える構造だったため。新しい動線を作るより、既に習得済みの操作をなぞるほうが学習コストが小さい。

**(4) 一覧パネルの内容:** `created_at` の降順（最近延期したものが上）で並べ、各行に料理名と時間帯を表示する。
同じ料理を重複して延期できるため（論点2の決定）、同名の行が並ぶことがある。

**枠に紐付いた食事を延期したときの挙動は意図どおりである（design review で確認済み）。**
枠はその日に残り、未割り当て状態になる。「パスタ枠」を残したまま中身だけ空く形であり、
枠エントリごと消さない。枠は日付と時間帯に対する計画であって、そこへ入る食事とは独立しているため。

**この論点で決めないこと:** 延期された食事を一覧から削除する操作（「もう食べない」）の要否、
延期された食事の件数をカレンダー上へ表示するか。いずれも今回のMUSTに含まれない。

### イテレーション0: mutation / query / Command / module 配置を確定する

#### 提案0

**推奨:** a。「延期されたものに日付を与える」という操作の本質をそのまま名指すため。

##### 戻す操作の mutation 名（主たる選択）

延期する側は `postponeMeal` で確定的である（ユビキタス言語「延期」の動詞形、目的語は食事）。
判断が要るのは戻す側である。

| | mutation | 読み | 弱点 |
| --- | --- | --- | --- |
| **a** | `schedulePostponedMeal(postponedMealId, date)` | 延期された食事の日程を決める | 「戻す」という語感は薄い |
| **b** | `resumePostponedMeal(postponedMealId, date)` | 延期された食事を再開する | 何を再開するのかが曖昧。延期は中断ではない |
| **c** | `restorePostponedMeal(postponedMealId, date)` | 延期された食事を元へ戻す | **元の日付には戻らない**ため不正確 |

この操作で実際に起きるのは「日付が未決だった食事に日付を与えて確定させる」ことである。
`schedule` はこれをそのまま名指す。`re` を付けないのは、元の日付へ復すのではなく新しい日付を
決めるためである。

##### 確定する contract 一覧

```graphql
postponeMeal(input: { mealId: Int! }): { postponedMealId: Int! }
schedulePostponedMeal(input: { postponedMealId: Int!, date: ISO8601Date! }): { mealId: Int! }
postponedMeals: [PostponedMealForList!]!
```

| contract | caller | 成功時のresult | 成功時のside effect |
| --- | --- | --- | --- |
| `postponeMeal` | 食事カードのアクション | 作られた `postponedMealId` | `meals` の行を削除し `postponed_meals` へ1件作成。紐付く `meal_frame_entries.meal_id` は `NULL` へ |
| `schedulePostponedMeal` | 延期一覧の確定パネル | 作られた `mealId` | `postponed_meals` の行を削除し `meals` へ1件作成。`meal_type` は延期された食事の値、`comment` は `NULL` |
| `postponedMeals` | 延期一覧パネル | `id` / `dishId` / `dishName` / `mealType` / `createdAt` | なし |

**失敗contract:**

| 条件 | error contract | state保証 |
| --- | --- | --- |
| `mealId` が存在しない、または他ユーザーのもの | `raise "指定した食事は存在しません。"` | data不変 |
| `postponedMealId` が存在しない（他端末で既に確定済み等） | `raise "指定した延期された食事は存在しません。"` | トランザクションrollback。`Meal` も作られない |

##### backend の責務配置

## 論点6: 料理を削除したとき、その料理を参照する延期された食事をどうするか

**ステータス:** 決定

**親論点:** 論点1

**種別:** TBDヒアリング

### イテレーション0: 料理削除時の扱いを確定する

#### 提案0

**推奨:** b。a は今回のscopeでは行き止まりを作るため。

##### 前提となる調査結果

`Business::Food::Dish::Usecase::RemoveCommand` は、その料理を参照する `meals` が1件でもあれば
削除を拒否する。

```ruby
# ユースケースがはっきり定まっていないので、定まるまで安全に倒す
raise "この料理は登録されている食事があるので削除できません。" if dish_record.meals.present?
```

`postponed_meals.dish_id` も `NOT NULL` であるため、何もしなければ参照先を失った行が残り、
一覧で料理名を引けなくなる。放置は不具合であり、選択肢に含めない。

##### 選択肢

**a. 既存のガードへ `postponed_meals` を加え、削除を拒否する**

```ruby
raise "この料理は延期された食事があるので削除できません。" if dish_record.postponed_meals.present?
```

既存の判断と完全に揃う。「定まるまで安全に倒す」という方針をそのまま延長する。

**b. 料理の削除時に、その料理の延期された食事も一緒に削除する**

`Dish` へ `has_many :postponed_meals, dependent: :destroy` を置く。削除前に確認ダイアログで件数を示す。

```text
この料理は延期リストに2件あります。料理を削除すると、それらも削除されます。よろしいですか？
```

##### a が今回のscopeで行き止まりを作る

論点4で「延期された食事を一覧から削除する操作」を非目標としたため、**延期リストから項目を取り除く手段は
日付を与えて確定させることだけ**である。

a を採ると、延期リストにだけ存在する料理を削除したいユーザーは次を強いられる。

1. 延期された食事に日付を与えて `Meal` にする（食べる予定がないのに）
2. カレンダーからその食事を削除する
3. ようやく料理を削除できる

`meals` に対する既存ガードでは、食事の削除操作が既に存在するためこの迂回は生じない。
延期された食事には削除操作がないため、同じガードを置くと行き止まりに近い状態になる。

##### b を推す理由

**延期された食事と食事では、料理が消えたときの意味が違う。**

- `meals` は「その日にそれを食べた」という**過去の記録**である。料理マスタが消えても記録の事実は残るため、
  安易に消せない
- `postponed_meals` は「いつかそれを食べたい」という**未来への意思**である。料理そのものを削除するなら、
  その料理を食べたいという意思も同時に失われる。意思だけが残っても指す先がない

料理を削除する行為自体が意図的で破壊的な操作であり、その料理を食べたいという意思の消滅は
その行為に含まれている。確認ダイアログで件数を示せば、黙って消えることも避けられる。

#### 提案背景

##### この提案が満たす必要のある条件

`postponed_meals.dish_id` は `NOT NULL` であり、参照先が消えた行を許すと一覧が壊れる。
何らかの扱いを決める必要がある。

##### 既存と揃えないことを選ぶ判断

architecture doc は「現在の他の命名との整合性は命名の根拠にならない」と述べ、整合性より本質を優先する
判断を求めている。同じ姿勢を挙動にも適用した。既存が `meals` をブロックしているのは
「ユースケースがはっきり定まっていない」ためであり、原理的な結論ではない。

今回は `postponed_meals` について、料理が消えたときの意味が `meals` とは異なることを確認できた。
整合性のために行き止まりを作るより、意味に従って別の扱いを選ぶ。

##### この提案で決めないこと

- 延期された食事を一覧から削除する操作の追加。論点4で非目標とした判断は維持する。
  b を採れば、それが無くても行き止まりは生じない

#### 提案0へのフィードバック

**結果:** a を採用。判断軸は「料理の削除は重い行為である」

> a。dishを消すという行為はかなり重い

提案0は「延期リストから項目を取り除く手段が確定させることだけであるため、a は行き止まりを作る」ことを
b の根拠にした。feedbackはこの摩擦を欠陥ではなく**適切な抵抗**と位置づけた。

料理の削除は重い行為であり、参照を先に片付けさせることは正当な要求である。参照が残っているのに
消せてしまうほうが危うい。提案0はこの摩擦をコストとしてのみ数え、料理削除の重さを判断軸に
入れていなかった。

### 決定

`Business::Food::Dish::Usecase::RemoveCommand` の既存ガードへ `postponed_meals` を加え、
延期された食事が1件でも存在する料理の削除を拒否する。

```ruby
raise "この料理は登録されている食事があるので削除できません。" if dish_record.meals.present?
raise "この料理は延期された食事があるので削除できません。" if dish_record.postponed_meals.present?
```

`Dish` へ `has_many :postponed_meals` を追加する。`dependent` は指定しない（既存の `has_many :meals` と同じ）。

**判断根拠:** 料理の削除は重い行為である。参照を先に片付けさせる摩擦は欠陥ではなく適切な抵抗であり、
参照が残ったまま消せるほうが危うい。既存が `meals` に対して「定まるまで安全に倒す」と判断したのと
同じ姿勢を、`postponed_meals` にも適用する。

**cascade削除を採らない理由:** `dependent: :destroy` は、料理を消すという一つの操作で
「いつか食べたい」という意思まで巻き込んで消す。確認ダイアログを添えても、削除の影響範囲が
料理マスタを超えて広がることに変わりはない。重い行為の影響範囲は広げず、狭く保つ。

**受け入れた帰結:** 論点4で「延期された食事を一覧から削除する操作」を非目標としたため、
延期リストにだけ存在する料理を削除したいユーザーは、延期された食事に日付を与えて `Meal` にし、
その食事を削除してから料理を削除することになる。この迂回は認識したうえで受け入れる。
料理の削除自体が稀で重い操作であるため、迂回の発生頻度は低い。

**あるべき姿（design review で確認済み）:** 本来は延期された食事を単体で削除するアクションを
用意すべきである。それがあれば迂回は生じず、料理削除のガードも自然に機能する。

今回それを作らないのは、この経路がエッジケースだからである。料理の削除自体が稀であり、
そのうち延期リストにだけ存在する料理を消したいケースはさらに稀である。
必要になった時点で延期単体の削除アクションを追加する。

この制約は steering の記録だけでなく、code 上のコメントまたは document にも残す（論点8で扱う）。
設計文書は次にこの箇所を触る実装者の目に入らないため、記録が steering 内に閉じると同じ検討が
ゼロからやり直される。

**今回の判断:** Phase 1 完了時点で commit・push を実行する。合意済み tasklist の
