### イテレーション0（論点1）: 現状の見た目を「意図」「v0 由来」「移行の残骸」に仕分ける

#### 認識合わせ0（論点1）

週カレンダーの見直し案は、まだ提案できない。
キャンバスの A/B/C は、何を守り何を変えてよいかを知らずに作ったためである。
現状には理由を持って選んだものと、移行の都合で残っただけのものが混ざって見える。

次の六項目について、読みが合っているか、違うならどういう意図かを聞きたい。
一言の回答でよく、この六項目以外に話したい意図があれば、そちらを優先する。

##### 1. この画面の主な仕事

- 事実: `/` は週カレンダーへ転送される。v0 のアプリ説明は「1週間・1ヶ月の献立を計画・管理するアプリ」である。カレンダー上の操作は、割当、枠、枠パターン適用、他の日へ、日付交換、延期と、組み替えが多い。
- 読み: 「今週の献立を組む・組み替える」が主で、「今日なにを食べるか見る」「食後に評価する」は従である。
- 聞きたいこと: 合っているか。いちばん多く開くのはどの場面か。

##### 2. 土曜始まりの週

- 事実: `START_FROM_SAT` で固定されている。コードには「自分以外も使うようになったらユーザ設定で選べるようにする」という TODO だけがある。
- 読み: 買い出しや週末の調理を起点に一週間を組む生活に合わせている。
- 聞きたいこと: 理由は何か。

##### 3. 料理ではない予定も「食事」として入れる

- 事実: 料理名に「出社」のような予定が入る使い方が、過去のスクリーンショットにある。
- 読み: カレンダーは料理の予定表というより「その食事をどうするか」の予定表であり、作らない食事も見えることが大事である。
- 聞きたいこと: 何を残したくて入れているか。料理と見え方を分けたいか、同列がよいか。

##### 4. 昼が橙、夜が青

- 事実: v0 と移行前の SCSS 変数は、昼が緑、夜が橙である。現状の色は #207（2026-03-08）で入った。変更の理由は読んだ範囲の記録に見つからなかった。
- 読み: 昼夜の見分けを強めるために変えた。色そのものへのこだわりは弱い。
- 聞きたいこと: 今の色に意図はあるか。

##### 5. カード上の常時表示アイコンと、その場で開く操作欄

- 事実: 1行目の食事編集・評価・その他は v0 のままで、ボタンは 28px である。カード全面のタップで開く挙動は v0 になく、#237（2026-03-22）で足された。その場で開く形を選んだ理由は「v0 準拠」としか残っていない。
- 読み: 全面タップは使ってみて足した実感ベースの意図である。常時表示は v0 由来で、★以外に強い意図はない。その場で開く形も v0 由来で、シートに変えても意図は壊れない。
- 聞きたいこと: どの操作をカード上に出しておきたいか。その場で開くことに意図はあるか。

##### 6. 重い見た目

- 事実: v0 は、枠線がグレー、「+」が 24px の控えめなボタン、今日は日番号の塗りつぶし、文字は Geist である。現状は、全体の枠線色の指定が移行で入らなかったため枠線が濃い。「+」は移行前の部品を流用した約 34×36px で、食事のない日は点線の「+」と二重になる。今日は輪郭だけで、フォントの指定はない。
- 読み: どれも意図ではなく移行の残骸である。
- 聞きたいこと: 合っているか。濃い枠線などを気に入って残しているものはあるか。

##### 回答で進むこと

回答ごとに、次のどれに入るかが決まる。

- 意図がある: 永続化する対象になる。置き場所は次の論点で決める。
- 残骸である: 直す候補になる。適用するかは別の論点で決める。
- どちらでもない、または未定: キャンバスで案を比べる題材になる。

### イテレーション2（論点1）: 週カレンダーのデザイン意図を一覧として確定する

#### 提案2（論点1）

週カレンダーのデザイン意図を、次の内容で確定する。

##### 原則

使う場面で必要な情報と操作の入口は、別の操作なしで見えている。
全ての操作を出すという意味ではない。

##### 場面ごとに見えていること

| 場面 | 見えていること | 理由 |
| --- | --- | --- |
| 1週間の献立を組む | 土曜から金曜までの全日と、各日の食事追加 | 土曜にまとめて買い物へ行くため、週は買い物の単位である。一日に副菜など二つ以上入れることがある |

| 毎日見る | 今日のクローズアップ、その週のイベント | 毎日見ており、食事はイベントに引きずられる |

##### 場面を通して守ること

- レシピ元は料理の一部である。同じ生姜焼きでも、どの生姜焼きかはレシピ元で決まる。
- どの時間帯かを一目で分かる。文字と色で示し、色だけに頼らない。カードの背景色は必須ではない。
- 操作は押しやすく、数が増えても破綻しない。以前のハンバーガーメニューは押しにくく、増えた時に破綻すると考えて変えた。
- イベントは本来、食事と別の表し方にする。実現の仕方と時期は別の論点で扱う。

##### 意図ではないもの

見直しで自由に変えてよい。

- 濃い枠線、「+」ボタンの大きさと形、今日の表現が輪郭だけであること、フォントが未指定であること
- 橙と青という色そのもの。おひさまと夜という連想の程度である

##### この決定に含めないもの

今回の範囲では決めない。
本人の回答がまだなく、見直し案を見ないと判断しにくいためである。
見直し案を議論する時に扱う。

- 他の日の評価の点数と入口の出し方
- 操作欄をその場で開くか、シートで開くか
- 料理コメントと食事コメント、区分アイコンの出し方
- 計画する場面と毎日見る場面の比重

#### 検討記録（論点1・イテレーション2）

> 意図は差分として出たものとしては、書いてもらったもので合ってる。コメントも出しておきたいね。次作る時用にわざわざ残しているコメントだから、隠されてて、見てみたら「だったら言ってよお」とかある。ワンタップの範囲は合ってる。

「差分として出たものとしては」は、この一覧が現状と A/B/C の差分から出た範囲であり、網羅ではないという留保と読む。
コメントの修正は本人が一意に指定したため、再度の確認を挟まず決定へ反映する。

### 決定（論点1）

週カレンダーのデザイン意図を次のとおりとする。
この一覧は現状と A/B/C の差分から出た範囲であり、網羅ではない。

原則は、使う場面で必要な情報と操作の入口が、別の操作なしで見えていることである。
全ての操作を出すという意味ではない。

| 場面 | 見えていること | 理由 |
| --- | --- | --- |
| 1週間の献立を組む | 土曜から金曜までの全日と、各日の食事追加 | 土曜にまとめて買い物へ行くため、週は買い物の単位である。一日に副菜など二つ以上入れることがある |
| 買い出しの材料を列挙する | 料理名、レシピ元、本ならページ | そのレシピを開くため。ページが分かれば目次から探さなくてよい |
| 料理を作る | 料理名、レシピ元、本ならページ、コメント | 開きたいページを知るため。コメントは次に作る時のために残しており、隠れていると作った後で気づくことになる |
| 毎日見る | 今日のクローズアップ、その週のイベント | 毎日見ており、食事はイベントに引きずられる |
| 今日食べたものを評価する | 今日の食事の評価を始める、ワンタップの入口 | 評価はたいてい今日食べたものについて起こる |
| 月全体を眺める | 一覧性（月ビュー） | 月で表示するほうが便利な時に使う（論点5の後の発言より） |

場面を通して、次を守る。

- レシピ元は料理の一部である。同じ生姜焼きでも、どの生姜焼きかはレシピ元で決まる。
- どの時間帯かを一目で分かる。文字と色で示し、色だけに頼らない。カードの背景色は必須ではない。
- 操作は押しやすく、数が増えても破綻しない。以前のハンバーガーメニューは押しにくく、増えた時に破綻すると考えて変えた。
- 週ビューの先頭は常に土曜である。今週分に限らず1ヶ月分などの献立を考える時も、一番上に土日があることで、位置から土日が分かる（論点2の決定より）。
- 複数週の献立は週ビューで決める。月ビューは一覧性が欲しい時に使うため、先頭が土曜であることは求めない（論点5の後の発言より）。
- 月ビューは週ビューと表示を共有し、専用の表示を作らない。こだわりのない所へ保守の手間をかけない（論点8の決定より）。
- 操作欄があることは初見でも分かる。行の右端に「…」を置く（論点3の決定より）。
- イベントは本来、食事と別の表し方にする。実現の仕方と時期はこの決定に含めない。

次は意図ではなく、見直しで自由に変えてよい。

- 濃い枠線、「+」ボタンの大きさと形、今日の表現が輪郭だけであること、フォントが未指定であること
- 橙と青という色そのもの。おひさまと夜という連想の程度である

次はこの決定に含めない。本人の回答がなく、見直し案を見ないと判断しにくいためであり、見直し案の議論で扱う。

- 他の日の評価の点数と入口の出し方
- 操作欄をその場で開くか、シートで開くか
- 区分アイコンの出し方
- 計画する場面と毎日見る場面の比重

## 論点2: 見直しで今日のクローズアップをどこに置くか

**種別:** TBDヒアリング

a を推す決め手は、週が一本の一覧のままで、同じ食事が二箇所に出ないことである。
土曜に開くと今日が先頭になるため、計画する場面と毎日見る場面が同じ形で両立する。

## 論点4: 開いた時に今日までスクロールするか

**ステータス:** 決定

**親論点:** 論点1

**種別:** TBDヒアリング

### イテレーション0（論点4）: 開いた時の初期位置を決める

#### 提案0（論点4）

週カレンダーを開いた時の初期位置を、次のどちらかにする。
推奨は a である。

##### a. 自動でスクロールしない

開くと常に土曜が先頭に見える。

- 良い点: 見るたびに見えるものが変わらない。今週も一番上が土日のままで、他の週と同じ枠組みで見られる。新しい処理が要らない。
- 代償: 1画面に収まらない週は、週の後半に今日まで手でスクロールする。
- 暫定性: 今の材料での判断である。見直した表示を使い、週の後半に今日まで届かないことが多ければ b を検討する。

##### b. 今週を開いた時だけ、今日までスクロールする

今週以外の週には今日がないため、他の週は土曜が先頭のままである。

- 良い点: 毎日すぐ今日が見える。評価の入口へも最短で届く。
- 代償: 開いた時に見える範囲が曜日で変わる。週の後半は土日が画面の外へ出る。開いた時に今日まで移動する処理を新しく作る。

##### 判断の材料

ボード D に、高さ 844px の範囲を示す赤い帯を付けた。帯は最初の1画面の目安であり、キャンバス上だけに出る。
Tweaks `todayWeekday` を「金」にすると、週の最後の日がこの帯に入るかを確かめられる。

#### 検討記録（論点4・イテレーション0）

論点2で今日を一覧の中で開く形に決めた時、自動スクロールを同じ案に含めていた。
本人の「見るたびに見えるものが変わるのもなぁ」が自動スクロールにも一部当たるため、別の判断として切り出した。

a を推す決め手は、論点2で本人が挙げた二つの理由である。
見るたびに見えるものが変わらないことと、一番上に土日があることの枠組みは、どちらも a のほうがそのまま満たす。
b は今週の開き方だけを他の週と変えることになる。

a の代償が実際にどれだけ起きるかは、週の高さによる。
現状は 2026-08-23 のスクリーンショットで7件の料理カードの高さが 985px であり、金曜のカードが 844px より下から始まる。
ボード D は枠線を減らしたが、レシピ元とコメントを省略せず出すため、週によって高さが変わる。
描画を確認していないため実際の高さは測っておらず、赤い帯で本人に見てもらう。

### 決定（論点4）

週カレンダーを開いた時に、自動でスクロールしない。

## 論点17: 現在の正本の写しと、状態ごとの見本を Claude Design に作るか

## 論点18: 別のセッションから Design System をどう辿らせるか

**ステータス:** 反映済み

**親論点:** 論点15

**種別:** レビュー指摘

### イテレーション0（論点18）: Design System への入口を文書へ置く

#### 提案0（論点18）

`frontend/docs/ai_guideline/development_standard/ui_design_management.md` の「Claude Design を使う時の進め方」で、Design System を使う場面を書き、URL を書く。

```diff
 - 作業場はリポジトリから作る。古くなっていたら、Design System の README に書いた commit から `git log` を見て最新化する。常に同期する努力はしない。
-- Design System に何を置くかは、その README に従う。claude.ai 上で「なにたべ Design System」という題名で探す。URL は public なこのリポジトリへ書かない。
+- Claude Design でこのリポジトリの画面を作る時と考える時は、Design System として「なにたべ Design System」（<URL>）を使う。何を置くかは、その README に従う。
 - 他のデザイン管理の仕組みへ移る時は、リポジトリを入力にする。変換の仕方は、移ることが決まった時に検討する。
```

`<URL>` には artifact の実際の URL を入れる。合意の前には、議論ファイルにも書かない。

あわせて `design.md` の「リスクと対策」で、記録へ書かない識別子を「artifact の URL」から「Design System 以外の artifact の URL」へ狭める。

#### 検討記録（論点18・イテレーション0）

本人の問い「別のセッションで/designスキル叩いても自然と参照されるの？」に、私はチャットで次のように答えた。

- 新しいキャンバスを作る時、Design type の指示は Design System の一覧を確認させる。既定の印が付いたものは聞かずに使う。今の「なにたべ Design System」には印がない。
- `ui_design_management.md` に、題名で探すと書いた。
- 今回のキャンバスは参照されない。

これに本人から次の指摘を受けた。

> 1の状況なら作りっぱなしでいいわけないじゃん。デザインのナレッジのところにデザインシステムのURLでも書かなきゃだめじゃん

##### 今の文書の不足

一つは、使う場面が書かれていないことである。
今の行は、Design System に何を置くかと、どう探すかだけを述べている。
新しいセッションがこの文書を読んでも、Claude Design で画面を作る時にこれを使えとは読めない。

もう一つは、題名だけでは一意に決まらないことである。
題名は変えられ、同じ題名の artifact も作れる。
人がこの文書から開くこともできない。

##### URL を書いてよいか

URL を書かないとしたのは、論点15の提案0で私が足したことである。
artifact の URL を識別子として一律に扱い、`confidentiality.md` の第1段（公開された時に、読んだ人が何をできるようになるか）を当てていなかった。
当て直すと次のとおりである。

- この artifact は private であり、開けるのは本人だけである。URL を読んだ人は開けない。
- URL は `claude.ai/artifact/` と artifact ごとの ID から成り、本人を示す情報を含まない。
- 本人が後で、リンクを知る人へ共有を広げると、誰でも開けるようになる。その場合も中身は、`globals.css` から写したトークン、public な README から写した画面の意図、Design System 自身の説明である。このリポジトリで既に公開されているものの写しであり、新しく知られることは実質ない。
- この前提は、公開できないもの（実データの料理名など）を Design System へ置かないことに依る。論点13の決定で「入れない」に既にある。

そのため、Design System の URL は書いてよいと判断した。
キャンバスの URL は対象にしない。キャンバスは議論ごとの作業場であり、次のセッションが辿る必要がないためである。

##### この文書が効く範囲

この文書が読まれるのは、frontend の文書を読み込んだセッションである。
`frontend/CLAUDE.md` から `@` で辿られるが、repository の root で始めたセッションは、frontend のファイルを読むまでこれを読み込まない。
`/design` が Design System を選ぶ時点で読み込まれているとは限らない。

`/design` で確実に使わせる手段は、claude.ai で既定に設定することである。
論点14で読んだ資料では、既定がなければ使うかを本人へ聞く。
`design.md` には、既定への設定は本人が行うとある。
この文書の行は、既定の設定を補い、人と frontend を扱うセッションへ入口を示すものである。

### 決定（論点18）

`frontend/docs/ai_guideline/development_standard/ui_design_management.md` の「Claude Design を使う時の進め方」に、Claude Design でこのリポジトリの画面を作る時と考える時は「なにたべ Design System」を使うことと、その URL を書く。
題名で探す指示と、URL を書かない指示は外す。

Design System の URL を public なリポジトリへ書いてよいのは、artifact が private であり、仮に共有を広げても中身がこのリポジトリで公開済みのものの写しだからである。
この前提は、公開できないものを Design System へ置かないこと（論点13）に依る。
キャンバスなど、Design System 以外の artifact の URL は引き続き書かない。

この行が読まれるのは frontend の文書を読み込んだセッションである。
`/design` で確実に使わせる手段は claude.ai での既定の設定であり、本人が行う。
