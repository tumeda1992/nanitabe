# 議論記録

## 論点1: 確定案をコードへ移す時に、ボードの値をどう渡すか

**ステータス:** 反映済み

**種別:** レビュー指摘

### イテレーション0（論点1）: 確定案との差の原因と、次に防ぐ置き場所を決める

#### 提案0（論点1）

`frontend/docs/ai_guideline/development_standard/ui_design_management.md` に、確定案をコードへ移す時の手順と、その失敗例を足す。

```diff
 ## Claude Design を使う時の進め方
 
 - MUST: 決まったことはリポジトリへ戻す。キャンバス上の変更は、戻すまで確定ではない。
+- キャンバスの確定案をコードへ移す時は、確定案のボードから値（色、余白、面、配置）を書き出し、実装の入力にする。「ボードのとおり」と参照するだけで渡さない。移した後は、ボードと同じ幅で画面を撮り、ボードと並べて差を確かめる。
 - 作業場はリポジトリから作る。古くなっていたら、Design System の README に書いた commit から `git log` を見て最新化する。常に同期する努力はしない。
```

```diff
 ## やってしまいがちな失敗
 
 - キャンバス上の変更だけで確定と扱う。作業場が消えると決定も消え、コードを読む人にも届かない。
+- 確定案のボードを参照するだけで、値を実装へ渡さない。実装する側が色や余白を推測し、確定案とずれる。週カレンダーの見直しでは、移した後に直す差が11点出た。
 - `tokens.json` を正本として直す。コードとずれ、次の最新化で失われる。
```

#### 検討記録（論点1・イテレーション0）

##### 何が起きたか

Phase 1〜6 でキャンバスの確定案をコードへ移した後、確定案と画面の間に、直す必要のある差が11点出た（`tasklist.md` の「確定案のボードとの差の記録」の差1〜3、差5〜12）。
見つけた経路は三つである。

- `visual-inspector` の受け入れ基準の検査で3点（差1〜3）。
- 私が画面のスクリーンショットとコードを確定案のボードと見比べて6点（差5〜10）。検査の報告にはなかった。
- その修正の再確認で2点（差11、差12）。

##### 原因

差は原因で三つに分かれる。

一つ目は、確定案の値が実装へ渡っていなかったことである。差1〜3、差6〜10 の8点がこれに当たる。
`design.md` は、確定案の内容を言葉で書き、細部は「確定案のボードのとおり」とした。
レシピ元の文字色、「評価する」の面と枠、枠の行の印の色、点数の色、操作欄の面などの値は、ボードにしかなかった。
`tasklist.md` も、実装の入力にボードを挙げていなかった。
「今週」については、`tasklist.md` が `h-11` とだけ書き、幅の下限を書いていなかった（差1）。
実装した側は値を推測し、確定案とずれた。

二つ目は、グローバル CSS の前提である。差5（`<a>` が content-box）と差12（`svg` が inline）がこれに当たる。
これは実装の後の doc-enricher の提案から `global_css.md` を足して扱った。

三つ目は、作り直した写しと実物の差である。差11 がこれに当たる。
ボードはコードを HTML で作り直したものであり、文字の幅や余白が実物と同じではない。
期間ラベルはボードでは収まっていたが、実物の 390px では切れた。
これは論点17で、写しが作った時点から近似になる理由として扱った性質であり、移した後に実物を撮って確かめる以外に防ぎ方がない。

検査が6点を見落としたのは、私が検査へ渡したのが受け入れ基準の項目であり、ボードとの見比べを依頼していなかったためである。

##### どこへ書けば次に防げるか

一つ目と三つ目は、Claude Design の確定案をコードへ移す時の手順の不足である。
`ui_design_management.md` の「Claude Design を使う時の進め方」は、決まったことをリポジトリへ戻すことは定めているが、確定案の値を実装へどう渡すかは定めていない。

task-design の skill の不足とは扱わない。
task-design は既に「実装中に新しい判断が生まれない状態」を設計の完了としている。
今回はその基準を満たさない `design.md` のまま実装へ進めたのであり、skill に問いが欠けていたのではない。
Claude Design のボードが見た目の仕様を持つという、このリポジトリでの使い方に固有の知識が欠けていた。

提案は、移す時に値を書き出して渡すことと、移した後にボードと並べて確かめることを一つの手順として書く。
前者は一つ目を、後者は三つ目と検査の見落としを防ぐ。
どちらか一方では、移す手順として成り立たない。

Tailwind v3 と v4 で色の値が違うことに起因する食い違い（差13 と Design System の `rating-text`）は、値の写し方という別の問いであり、この論点に含めない。

### 決定（論点1）

`frontend/docs/ai_guideline/development_standard/ui_design_management.md` に、次の二つを足す。

- 「Claude Design を使う時の進め方」: キャンバスの確定案をコードへ移す時は、確定案のボードから値（色、余白、面、配置）を書き出して実装の入力にする。「ボードのとおり」と参照するだけで渡さない。移した後は、ボードと同じ幅で画面を撮り、ボードと並べて差を確かめる。
- 「やってしまいがちな失敗」: 確定案のボードを参照するだけで値を実装へ渡さず、実装する側が推測して確定案とずれる。週カレンダーの見直しでは、移した後に直す差が11点出た。

値を書き出して渡すことは、値が実装へ渡っていなかった8点を防ぐ。
ボードと並べて確かめることは、ボードと実物の作りの違い（差11）と、受け入れ基準だけを渡した検査の見落としを防ぐ。
二つで一つの手順であり、片方だけでは移す手順として成り立たない。

task-design の skill は直さない。
「実装中に新しい判断が生まれない状態」を設計の完了とする基準は既にあり、今回はそれを満たさないまま実装へ進めたためである。

## 論点2: Tailwind の色名の値をどこから取るか

**ステータス:** 反映済み

**種別:** レビュー指摘

### イテレーション0（論点2）: v3 の値で書いた食い違いを、次に防ぐ置き場所を決める

#### 提案0（論点2）

`frontend/docs/ai_guideline/development_standard/ui_design_management.md` の「Claude Design を使う時の進め方」に、色の値の取り方を足す。

```diff
 - 作業場はリポジトリから作る。古くなっていたら、Design System の README に書いた commit から `git log` を見て最新化する。常に同期する努力はしない。
+- 色の値を書く時（作業場のトークン、画面を確かめる時の期待値）は、Tailwind の色名から値を思い出して書かない。Tailwind v4 の定義（`node_modules/tailwindcss/theme.css`）か、ブラウザで計算された値から取る。同じ色名でも v3 と v4 では値が違う。例えば `amber-700` は v3 では `#b45309`、v4 では `oklch(55.5% 0.163 48.998)`（計算値 `rgb(187, 77, 0)`）である。
 - Claude Design でこのリポジトリの画面を作る時と考える時は、…
```

#### 検討記録（論点2・イテレーション0）

##### 何が起きたか

点数の色について、値の食い違いが二箇所で起きた。

- Design System の `tokens.json` の `rating-text` を `#b45309` と書いた。コードの `text-amber-700` は、このリポジトリの Tailwind 4.2.1 では `oklch(55.5% 0.163 48.998)` で、計算値は `rgb(187, 77, 0)` である。`#b45309` は Tailwind v3 の `amber-700` の値である。
- `visual-inspector` への検査の依頼で、点数の色の期待値を `rgb(180, 83, 9)`（= `#b45309`）とした。検査は計算値 `rgb(187, 77, 0)` との差を報告し、調べた結果、不具合ではなかった（`tasklist.md` の差13）。

##### 原因

どちらも、私が `amber-700` という色名から v3 の値を思い出して書いたことによる。
コードの値は Tailwind v4 の定義で決まり、リポジトリの中には値として現れない。
`globals.css` の CSS 変数は値を持つが、`amber-700` や `zinc-700` のような Tailwind の色名をコードが直接使う場合、値の正本は Tailwind の定義になる。

同じ色名でも、v3 と v4 で値が違うものと、ほぼ同じものがある。
`zinc-700` は v4 で `oklch(37% 0.013 285.805)`、計算値 `rgb(63, 63, 70)` で、v3 の `#3f3f46` と一致した。
`amber-700` ははっきり違う。
そのため、記憶で書くと、合っている色と違う色が混ざり、どれが違うかに気づきにくい。

##### どこへ書けば次に防げるか

`ui_design_management.md` は「作業場はリポジトリから作る」と定めているが、Tailwind の色名のように値がリポジトリに現れないものをどこから取るかは書いていない。
作業場の写し直し（Phase 7 と、その後の最新化）と、画面を確かめる時の期待値の両方で同じ問いが起きるため、一つの行として足す。

`global_css.md` には置かない。
`global_css.md` は全体に効く CSS が Tailwind の前提と違う点を扱い、色の値の取り方はその範囲ではないためである。
`frontend/README.md` の Tailwind の節にも置かない。自動では読み込まれず、作業場を作るセッションへ届かないためである。

### 決定（論点2）

`frontend/docs/ai_guideline/development_standard/ui_design_management.md` の「Claude Design を使う時の進め方」に、色の値の取り方を足す。
作業場のトークンと、画面を確かめる時の期待値で色の値を書く時は、Tailwind の色名から値を思い出して書かず、Tailwind v4 の定義（`node_modules/tailwindcss/theme.css`）か、ブラウザで計算された値から取る。
例として、`amber-700` の v3 と v4 の値を書く。

コードが Tailwind の色名を直接使う時、値の正本は Tailwind の定義であり、リポジトリの中には現れないためである。
色名によって v3 と一致するものと違うものがあり、記憶で書くと違いに気づきにくい。

`global_css.md` と `frontend/README.md` には置かない。
前者は全体に効く CSS が Tailwind の前提と違う点を扱い、後者は自動では読み込まれないためである。
