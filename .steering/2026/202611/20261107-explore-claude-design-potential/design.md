# Design: Claude Design のポテンシャルを知り、適用できるものを nanitabe へ適用する

## 元の依頼内容

最初の依頼（`/design`）:

```text
CloadDesign使ったことないから使ってみたい。このリポジトリでやるなら何やるのがいい？
```

キャンバスの提示を受けた後の依頼:

```text
えー、どれを選ぶかという結論から話すんじゃなくて、これをたたき台に私の既存のデザイン意図を話してナレッジの永続化をしてもらったり、ブラッシュアップ案を話すの楽しそうだな。task-design、まぁやるのはfaciliate-discussionを起動したいだけなんだけど記録のスナップショットを残すためにtask-designをsteeringディレクトリ作って。steeringやtask-designにはお題目必要だから、ClaudeDesignで何ができるかポテンシャルを知る。その中で適用できることがあるならついでに適用しちゃうって感じで。
```

---

## TL;DR

Claude Design を使ったことがないため、週カレンダーを題材に何ができるかを知る。
週カレンダーのキャンバス（現状の再現と、A 献立リスト・B 今日から・C 昼夜マス目の三方向）をたたき台に、ユーザーの既存のデザイン意図を聞いて永続化する。
あわせて見直し案を話し、適用できるものがあれば適用する。

終了時には、デザイン意図が永続化され、キャンバスで固めた見直しが週カレンダーへ適用されている。

## 完成後の姿

### 調査・比較・技術検証によるfindings

**未知だった問い:**

- Claude Design で何ができ、そのうち nanitabe のどの作業に使えるか。
- 推測で決められなかった理由: ユーザーが未使用であり、機能の範囲は提供元の資料を読まないと分からないため。

**調査・再現条件:**

**可能になった判断と限界:**

- 可能になった判断: キャンバスは、本人の意図を引き出す叩き台と、案を比べる場として使える。正本はリポジトリとし、Claude Design は作業場とする。
- 本人の意図を聞かずに作った案（A/B/C）は意図を壊していたが、それへの反応から意図を引き出せた。
- まだ言えないこと: 資料の記述のみの項目が実際に使えるか。キャンバスの案がどこまでそのままコードへ移るか（適用の後に追記する）。
- 反証条件: 実際の操作で資料と異なる挙動が観測された場合、該当行を訂正する。
- 再検証trigger: Design type または Design System type の release が変わった時。

**今回は試さないが、知っておく能力:**

本人が知っておきたいと述べたものであり、この作業では試さない。
いずれも資料を読んだ範囲の理解で、実際には動かしていない。
見直す条件はそれぞれに書く。

効きそうなもの:

- キャンバスを手で直して、コードへ反映する
    - ボード上で文字を打ち替えたり、properties panel で余白や色を変えたりでき、Claude はその変更を読み取れる。文章で指示するより速い微調整になる可能性がある。
    - 試す条件: 次にキャンバスで見た目を微調整する時。
- イベントの別の表し方を、作る前に試す
    - バックエンドを触らずに、見た目と操作感を先に確かめられる。ボード D の Tweaks `separateEvents` が簡易版である。ボード間のリンクを使えば、登録の流れまで触れる試作にできる。
    - 試す条件: イベントを食事と別に表す作業へ着手するかを判断する時。
- キャンバス上のコメント
    - ボードの特定の場所へコメントを残すと、Claude が tool で読んで返信できる。場所を文章で説明しなくて済む。
    - 試す条件: 次にキャンバスで見た目を確認する時。

運用が変わったら効くもの:

- `/design-sync` で Design System の更新を任せる
    - コードから Design System へ写す作業を任せられる。向きは正本をリポジトリとする方針と合う。同期する形では artifact 側が読取専用になる。2026-11-07 の作業 session では使えなかった。
    - 試す条件: 手で写す作業が面倒になった時。
- 実部品をキャンバスへ置く
    - 実際の部品を束ねた `components/bundle.js` を Design System に持たせる。先に、表示部分をデータ取得から切り出す改修が要る。
    - 試す条件: 画面を何度も作り直すようになり、改修に見合う時。
- デザインツールから取り込む
    - Design System type に `from-design-tool.md` という資料がある。他のデザイン管理の仕組みとの行き来に関わる可能性があるが、資料は読んでいない。
    - 調べる条件: 他のデザイン管理の仕組みへ移ることを検討する時。

今回は薄そうなもの:

- deck、motion、doc への展開、PNG・PDF の書き出し、Canva への送信。本人用のアプリでは使い道が少ないと見ている。発表や共有の必要が出た時に見直す。
- 選択した要素を指示に使う機能。会話の横で artifact を開くと選択内容が届くとされるが、この作業の会話では一度も届かなかった。ターミナルから使えないのかは確かめていない。デスクトップアプリ等で開いて作業する時に確かめる。

### 週カレンダーの画面

週ビューと月ビューは同じ部品を使い、同じ見た目になる。
月ビューの先頭は月の1日のままである。

**完成後のwireframe:**

```text
┌───────────────────────────────────────────────┐
│ <  今週  >      11/7 - 11/13     [週] [月] :  │ sticky。ボタンは 44px
├──────┬─────────────────────────────────┬──────┤
│  7   │ [昼](区) 焼きそば            …  │ [+]  │ 土曜が先頭。日番号と曜日は青
│  土  │ [夜](区) 豚の生姜焼き  ★4    …  │      │
│      │          レシピ本 P42           │      │
│      │          玉ねぎを先に炒める     │      │
├──────┼─────────────────────────────────┼──────┤
│  8   │ [夜] 枠 週末枠              削  │ [+]  │ 枠の行の右端は削除
│  日  │                                 │      │
├──────┼─────────────────────────────────┼──────┤
│ (11) │ 今日                            │ [+]  │ 今日。背景を薄く敷く。
│  水  │ [夜](区) 親子丼              …  │      │ 日番号は塗りつぶし。
│      │          料理研究家のサイト     │      │ 料理名は 20px の太字
│      │          つゆは少なめが好み     │      │
│      │          [★ 評価する]           │      │ 44px
├──────┼─────────────────────────────────┼──────┤
│ 13   │ 未定                            │ [+]  │ 食事も枠もない日
│  金  │                                 │      │
└──────┴─────────────────────────────────┴──────┘
```

`(区)` は区分アイコン、`…` は操作欄を開くボタン、`削` は枠の削除である。
日の間の区切りは `border-border` の細い線だけとし、カードの枠線は付けない。

**配置と強調の意図:**

- 日番号と曜日を左の列に置く: 土曜を一番上に固定し、複数週を見ても位置と色で土日が分かるようにする。
- レシピ元とコメントを料理名の下に省略せず出す: 買い出しと調理で操作なしに見えるようにする。切り詰めると、どの料理かが分からなくなる。
- 「+」を各日の右端に常に置く: 食事の有無によらず、同じ位置で追加できるようにする。薄い灰色の背景で「…」と区別する。
- 今日の行だけ大きくし、評価のボタンを置く: 順序を変えずに今日を際立たせ、評価はたいてい今日の出来事であるため入口を今日へ絞る。

**今回変わる状態別の見え方:**

| 状態 | 表示 | 操作可否 | 次の操作 |
| --- | --- | --- | --- |
| 今日以外の日の食事 | 昼夜の印、区分アイコン、料理名、点数、レシピ元、コメント | 「…」と行で操作欄を開ける。評価のボタンはない | 操作欄の「評価」から評価を始める |
| 今日の食事 | 「今日」の見出し、大きい料理名、レシピ元、コメント。点数はボタンの中に出す | 「評価する」または「★4 評価を変更」のボタンで評価を始める | 既存の評価モーダルが開く |
| 操作欄を開いた行 | 行の下に既存の操作の一覧を4列で出す | 既存の全操作 | 既存のとおり |
| 食事のない日 | 枠がなければ「未定」。点線の「+」はなくす | 右端の「+」で追加 | 既存の食事登録モーダルが開く |
| 移動、交換、割当の操作中 | 同じ行の表示。「+」「…」「評価する」と枠の削除は出さない | 日付を押すと選択になる | 既存のとおり |

週ビューのヘッダーの「今週」と月間ビューのアイコンは、`<a>` の既定の青と下線をやめ、他のボタンと同じ文字色にする。

**inputの供給元:**

| input | 供給元 | 受渡し経路 | 未取得・失敗時 |
| --- | --- | --- | --- |
| `isToday` | `DateCard` が `isSameDay(date, new Date())` で求める | `DateCard` → `MealCard` の新しい prop。省略時は `false` | なし |
| `meal`、`frameEntries` と他の prop | 既存のとおり | 変更なし | 既存のとおり |

**部品ごとの変更:**

- `Calendar/index.tsx`: 日の一覧の `gap-1.5 px-2 py-2` をやめ、区切り線で並べる。
- `DateCard.tsx`
    - root は `grid grid-cols-[52px_minmax(0,1fr)_44px] border-b border-border py-0.5` とする。今日は `bg-muted/50` を足し、`ring` はやめる。`data-testid` と `data-today` は保つ。
    - 日番号は 26px の丸で `text-[15px] font-semibold` とする。今日は `bg-primary text-primary-foreground` である。土曜は `text-blue-600`、日曜は `text-red-600` とし、他の日の曜日は `text-muted-foreground` とする。
    - 今日は行の上に `今日` の見出し（`data-testid="dateCard-todayLabel"`）を出す。
    - 食事も枠もない日は `未定`（`data-testid="dateCard-undecided"`）を出す。点線の追加エリア、そのモーダル、`AddMealTabs` の参照は消す。
- `MealCard/index.tsx`
    - prop に `isToday?: boolean` を足す。
    - カードの枠線、背景色、左のカラーバーをやめる。昼夜の印は `size-[22px] rounded-md` で、背景は `bg-lunch/15`、`bg-dinner/15`、`bg-breakfast/15` とする。
    - 常時表示の「食事編集」のボタンをやめる。操作欄の中の同じ操作は残す。
    - 「その他のアクション」のボタンを 44px にし、ラベルは保つ。行全体を押して開く動きと、再度押しても閉じない動きは保つ。
    - レシピ元は10文字の切り詰めをやめ、折り返す。`P{page}` の形は保つ。料理コメントの `line-clamp-2` と、食事コメントの `italic` をやめる。
    - 点数は今日以外の日に料理名の右へ出す。`mealCard-evaluation-{id}` は保つ。
    - 今日は料理名を `text-xl font-bold` にし、評価のボタンを置く。`aria-label="評価"` を保ち、表示の文字は「評価する」または「★{score} 評価を変更」とする。`stopPropagation` を行い、操作モード中は出さない。
- `FrameCard/index.tsx`: 枠線、背景色、左のカラーバーをやめ、`MealCard` と同じ行の形にする。削除のボタンを 44px にする。カードを押すと登録モーダルが開く動きは保つ。操作中は削除のボタンを出さない。`DateCard` から `isDisplayCalendarMode` を新しい prop `canDelete` として渡し、省略時は `true` とする。
- `MealIcon/AddMealIcon.tsx`: 外側を 44×52px の押せる範囲とし、中を `size-8 rounded-lg bg-muted` の「+」アイコンにする。使わなくなる `AddMealIcon.module.scss` は消す。`addMealIconOpener` は保つ。
- `CalendarHeader/index.tsx`: ボタンを 44px にする。リンクへ `text-foreground no-underline` を足す。
- `base.css` は `div`、`span`、`p` へ `color: #333` を当てており、親から文字色を継承できない。文字色は対象の要素自身へ指定する。`base.css` は変えない。

見た目に関わる決定は次のとおりである。

- 今日のクローズアップは、土曜から金曜の順のまま今日の行だけを大きくする。材料の列挙に使うため土曜始まりを保ち、見るたびに見えるものが変わらないようにする。1ヶ月分などを考える時に、一番上に土日があることが視覚的な枠組みになる。一覧を今日から始める形は、これらの理由で採らない。今日を上に固定する形は、今日の食事が二箇所に出て、土曜はその重複が先頭に並ぶため採らない。代償として、今日の位置が曜日で変わり、評価の入口も動く。
- 操作欄の入口は「…」で示す。現状のカードと同じ印である。「⌄」は操作欄の開き方が変わると意味がずれるため採らない。
- 開いた時に自動でスクロールしない。数週分を続けて決める時に、今週だけ動きが変わるとノイズになるためである。代償として、1画面に収まらない週は週の後半に手でスクロールする。これは今の材料での判断であり、週の後半に今日まで届かないことが多ければ、今週だけスクロールする形を改めて検討する。
- 操作欄は行の下へその場で開く。意図の面ではシートと差がつかず、現状のままで済むためである。
- 今日以外の日は点数だけを出す。評価はたいてい今日の出来事であり、全ての行にボタンを置くと料理名の幅が減るためである。代償として、翌朝に昨日の分を評価する時は2タップになる。
- 区分アイコンは残す。現状どおりで手間がかからず、主菜と副菜の組み合わせを一目で確かめられるためである。
- 行の背景色は付けない。重さを取る方向であり、文字があるため色だけに頼らずに済むためである。代償として、時間帯の判別は現状より目立たなくなる。
- 月ビューは週ビューと共有し、専用の表示を作らない。こだわりがなく、保守の手間を増やさないためである。月ビューへの具体的な要望が出たら、1日1行の形を改めて検討する。

### documentationによって成立する知識体系

**形式知化する対象:**

週カレンダーの画面の意図は、これまで文書になく、コードと過去の design からは読み取れなかった。
例えば操作欄をカード内へ置いた理由は「v0 準拠」としか残っていないが、実際の理由はハンバーガーメニューの押しにくさと、機能が増えた時の破綻である。
UIデザインの正本の扱いも決まっていなかった。

**読者と成立させる判断:**

| 読者 | 利用場面 | codeや過去会話を再調査せず可能になる判断・action | 入口 |
| --- | --- | --- | --- |
| カレンダーの表示を変える人（AI agent を含む） | 週ビューと月ビューの表示や操作を変える時 | 何を守り、何を変えてよいかを、本人へ聞き直さず判断できる | `frontend/src/components/calendar/README.md` の「画面の意図」 |
| frontend のUIを考える人（AI agent を含む） | Claude Design を使う時、デザインの置き場所を決める時 | 正本をどこに置き、作業場に何を任せるかを判断できる | `frontend/docs/ai_guideline/development_standard/ui_design_management.md` |

**snapshotと維持規律:**

| 正しいsnapshot | single source of truth | 更新owner | 更新trigger | 腐敗signal |
| --- | --- | --- | --- | --- |
| 本人が持つカレンダーの画面の意図 | `frontend/src/components/calendar/README.md` の「画面の意図」 | カレンダーの表示を変える作業の担当 | 意図に関わる表示や操作を変える時 | README と画面の食い違い |
| UIデザインの管理方針 | `frontend/docs/ai_guideline/development_standard/ui_design_management.md` | 方針を変える作業の担当 | 正本の置き場所や Claude Design の使い方を変える時 | 実際の運用との食い違い |

**完成後のdocument構造:**

- `frontend/src/components/calendar/README.md`: 「不変条件・契約」と「変更ガイド」の間に「画面の意図」節を持つ。一覧は現状と A/B/C の差分から出た範囲であり、網羅ではない。他の画面で同じ原則が成り立つと分かった時点で、上位の文書への移動を検討する。
- `frontend/docs/ai_guideline/development_standard/global_css.md`: 実装の後の doc-enricher の提案から足した。preflight を読み込まないことと `base.css` の要素指定が Tailwind の前提と違う点、class の書き方、今回起きた失敗、全体のリセットで直さない理由を持ち、同じ directory の `README.md` から `@` で参照される。
- `frontend/docs/ai_guideline/development_standard/ui_design_management.md`: 「正本と作業場」「正本の置き場所」「Claude Design を使う時の進め方」「やってしまいがちな失敗」を持ち、同じ directory の `README.md` から `@` で参照される。他のリポジトリでも同じ方針を使う時に、plugin の標準への移動を検討する。今の根拠はこのリポジトリの一件だけであるため、今はここに置く。

正本の扱いは次のとおりである。
正本はこのリポジトリに、ツールに依存しない形で持つ。
Claude Design のキャンバスと Design System は作業場であり、消えても失うものがない状態を保つ。
W3C 形式のトークンのファイルを正本にして変換する形は、変換の仕組みの保守が常に要るため採らない。
これは今の条件での判断であり、他のツールへ移ることが決まった時に、変換の仕方を改めて検討する。

### Claude Design の Design System

claude.ai 上の private な artifact「なにたべ Design System」として作成済みである。
見て判断するために、コードへの適用の前に作った。適用の後に写し直す。
これは正本ではなく、Claude と考える時の思考キャッシュである。

入れるものは、色のトークン（背景、文字、線、昼夜朝の印、枠、星）、文字、間隔、角丸のトークン、表紙、README である。

README には次を書く。

- この Design System がどういう存在か。思考キャッシュであり、正本はリポジトリであること
- 何を置き、何を置かないか。後の作業でこれに沿って育てられるようにする
- 写した commit と、最新化の方法。古くなっていたら `git log` を見て最新化する
- 画面の意図の写し。`frontend/src/components/calendar/README.md` から写す
- 部品の呼び名と役割（日の行、食事の行、昼夜の印、「+」、「…」）

部品のプレビューと `bundle.js` は入れない。
手書きのプレビューは画面を変えるたびにずれ、実部品はデータ取得と結びついており束ねられないためである。
これは今回の範囲の判断であり、表示部分を切り出す機会ができたら改めて検討する。
案の比較と決定の経緯、実データの料理名、未決の事項も入れない。

既定の Design System への設定は本人が行う。
`/design-sync` は使わない。

## 要件（Requirements）

### MUST（必達）

- 議論の提案、応答、決定を `task-design-discussion.md` へ記録する。
- 週カレンダーの見直しは、[画面の完成形](#週カレンダーの画面)と `frontend/src/components/calendar/README.md` の「画面の意図」を満たす。
- 既存の操作（追加、編集、評価、料理編集、名前コピー、他の日へ、日付交換、延期、枠解除、削除、枠への登録と削除）を失わない。
- 週ビューの先頭は土曜のままである。
- 料理、レシピ元、コメントの実データを成果物へ書かない。

### SHOULD（できれば）

- 既存の `data-testid` と `aria-label` を保ち、spec の変更を見た目に関わるものへ留める。

### MAY（あれば嬉しい）

なし

### 非目標

- 料理検索など、カレンダー以外の画面の濃い枠線は今回直さない。枠線の全体指定はカレンダー外の5 file へ効くため、今回の見直しへ混ぜない。各画面を見直す時に扱う。
- `base.css` の文字色の指定は今回変えない。影響がカレンダーの外へ及ぶため、同じく各画面を見直す時に扱う。
- 区分アイコンの区分ごとの色は今回活かさない。本人の意図を聞いておらず、現状の見え方を変えないためである。
- イベントを食事と別に表すことは今回行わない。データの変更を伴うためであり、取り組む時に別の issue を立てる。
- 未使用に見える `useFloatModal` と `NextWeekDisplayButton` のコードは今回消さない。今回の見直しに不要であるためである。
- フォントは今回指定しない。本人の意図を聞いておらず、見直しの中心でないためである。
- 全画面の現在の見た目を写した正本の写しと、状態ごとの画面や部品のバリアントの写しを、Claude Design に作らない。正本はコードであり、写しは作り直しであるため作った時点からずれ、最新に保つ手間がかかるためである。議論を始める時は、対象の画面の現状をその都度コードから作る（論点17）。
