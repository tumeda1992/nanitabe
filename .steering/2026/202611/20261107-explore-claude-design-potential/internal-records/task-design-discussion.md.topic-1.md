## 開始context

Claude Design で何ができるかを、週カレンダーを題材に知る作業である。
たたき台として、claude.ai 上のキャンバス「このリポジトリで Claude Design を試す」に、現状の再現と三つの方向（A 献立リスト、B 今日から、C 昼夜マス目）を置いた。

ここでいう「デザイン意図」は、見た目や操作のうち、ユーザーが理由を持って選び、見直しでも守りたいものを指す。
v0 の生成物をそのまま受け取っただけのものや、移行の都合で残っただけのものは含まない。

この論点で決めるのは、現状のどの要素がデザイン意図かである。
意図の保存先と、見直し案の採否は別の論点で扱う。

開始時の既決条件は、A/B/C のどれを選ぶかの結論から始めないこと、ユーザーの既存のデザイン意図を聞いて永続化すること、見直し案を話すことである。
残る不足は、記録に理由が残っていない要素について、本人の意図である。

### 調査: 現状の週カレンダーの各要素はどこから来たか

#### 問い・探索範囲・方法

要素ごとに由来が分かれば、本人へ聞くべき項目を絞れる。
由来は、v0 から受け取ったもの、移行で変質したもの、v0 の後に足したものの三つに分けて確かめた。

- 現状: `frontend/src/components/calendar/` の `DateCard.tsx`、`MealCard`、`FrameCard`、`CalendarHeader`、`frontend/src/app/globals.css`、`frontend/src/components/base/base.css`
- v0: `~/src/github.com/tumeda1992/nanitabe_v0_design` の `app/globals.css`、`app/layout.tsx`、`components/calendar/day-column.tsx`、`components/calendar/dish-card.tsx`
- 過去の記録: `.steering/2026/202603/` の feature-201 系の design、`.steering/2026/202608/` の二件の design、`.kiro/steering/product.md`
- 見え方: `frontend/inspect/visual/tmp/20260823-fix-dish-card-tap-copy-naming/phase-1/01_calendar_with_cards.png`（390×985）
- 文言検索: `frontend/docs`、`backend/docs`、`AGENTS.md` を「デザイン方針」「デザイン意図」「UI方針」「デザインシステム」で検索

#### v0 から受け取っているもの

次の要素は v0 のソースと一致した。

- 日付カードの縦積み（`rounded-xl border bg-card px-2.5 py-1.5`）
- 今日の `ring-2 ring-primary/40`
- 料理カードの左カラーバー
- 1行目の区分アイコン・料理名・昼夜ラベル・常時表示アイコン（`size-7`）
- 下部へ開く `grid-cols-4` の操作欄

v0 のアプリ説明は「1週間・1ヶ月の献立を計画・管理するアプリ」である。

#### v0 と現状で違うもの

- 枠線の色
    - v0 は `@layer base { * { @apply border-border ... } }` を持つ。現状の `globals.css` にこの指定はない。
    - `border` class は色を指定しないため、2026-08-23 のスクリーンショットではカードの枠線が濃く出ている。
- 「+」ボタン
    - v0 は `size-6` の ghost ボタンである。
    - 現状は移行前の `AddMealIcon` を流用しており、スクリーンショットで約 34×36px の灰色ボタンである。食事がない日は点線の「+」も出るため、一日に二つ並ぶ。
- 今日の表現
    - v0 は `ring` に加えて日番号を `bg-primary` で塗りつぶす。
    - 現状は `ring` のみである。`.steering/2026/202603/20260308-feature-201-ph3-implement-calendar-daycolumn-card-view/design.md` の受け入れ基準にも `ring` だけが書かれている。
- 文字
    - v0 は Geist を読み込む。現状の `frontend/src` の CSS・SCSS・TSX に `font-family` の指定はない。
    - `base.css` が `div`、`span`、`p` 等へ `color: #333` を指定している。親から継承するはずの `text-muted-foreground` や区分アイコンの色が、この指定で打ち消される箇所がある。スクリーンショットのレシピ元と区分アイコンの濃さと整合する。
- 昼夜の色
    - v0 は昼が `oklch(0.75 0.12 140)`（緑）、夜が `oklch(0.72 0.16 60)`（橙）である。移行前の SCSS 変数も `$lunch-green`、`$dinner-orange` で、同じ割り当てである。これらの SCSS 変数は定義だけが残り、参照は見つからなかった。
    - 現状は昼が `hsl(34 100% 50%)`（橙）、夜が `hsl(221 83% 53%)`（青）で、commit `756d41e`（#207、2026-03-08）で入った。

#### v0 の後に足されたもの

朝食、枠、枠パターン、延期、「他の日へ」「日付交換」の配置は v0 の後の機能追加である。
カード全面のタップで操作欄を開く挙動は v0 になく、`14bd136`（#237、2026-03-22）で入った。
v0 の操作欄は「…」ボタンの開閉だけである。

#### 記録の範囲内で理由が見つからなかったもの

- 文言検索の範囲に、デザイン方針を述べた文書はなかった。`.kiro/steering/product.md` は機能の一覧である。
- インライン展開の理由は、`.steering/2026/202603/20260308-feature-201-ph4-implement-dishcard-meal-display/design.md` に「v0 準拠」とだけある。
- 昼夜の色を変えた理由は、読んだ範囲の design に見つからなかった。同じ design は新しい色を要件として書くだけである。
- 土曜始まりは `START_FROM_SAT` の固定と「自分以外も使うようになったらユーザ設定で選べるようにする」という TODO だけで、理由はない。

これらは読んだ範囲での不在であり、`.steering/` の全件を通読した結果ではない。

#### 確認していないこと

v0 は起動しておらず、比較はソースの読解である。
現状の見え方の根拠は 2026-08-23 のスクリーンショットであり、その後も `MealCard` は変更されている。最新の描画は確認していない。
`visual-inspector` は実行していない。表示の変更が論点になった時点で実測する。

#### 言える範囲と次の action

要素を、理由が記録にあるもの、v0 から受け取っただけに見えるもの、移行で変質したように見えるものに分けられた。
ただし「v0 から受け取っただけ」でも、本人が気に入って残している可能性があり、記録からは確定できない。
そのため案を作る前に本人へ確認する。

### 認識合わせ: 本人にしか確定できない前提はどれか

#### 共有できる事実と、現在の読解

調査の結果、次の六項目は事実だけでは意図が決まらない。

- 画面の主な仕事。操作の種類からは計画と読めるが、実際に開く場面は記録にない。
- 土曜始まりの理由。固定値だけがある。
- 料理ではない予定を食事として入れる理由。使い方は見えるが、目的は記録にない。
- 昼夜の色。変更の事実はあるが理由がない。
- カード上の常時表示とその場での展開。全面タップは後から足した実感ベースに見え、他は v0 由来に見える。
- 濃い枠線などの重い見た目。移行の残骸に見えるが、気に入っている可能性は否定できない。

#### 本人にしか確定できない前提

六項目それぞれについて、読みが合っているか、違うならどういう意図かを聞く。
回答により、守る意図、直す候補、キャンバスで比較する題材のどれに入るかが変わる。
A/B/C の採否はここへ混ぜない。

### 調査: 週の後半に開いた時、今日は見えるか

#### 問い・探索範囲・方法

回答の「土曜始まり」と「毎日見る」を合わせると、週の後半に開いた時に今日が画面の下へ行く可能性がある。
`frontend/src` の `.ts`、`.tsx`（spec を除く）を `scrollIntoView`、`scrollTo`、`scrollTop` で検索し、今日へ移動する処理の有無を確かめた。

#### 見つかった事実

#### 言える範囲と限界

現状は、週の後半に開くと今日のカードへスクロールが要る可能性が高い。
別名の処理や CSS による位置調整は検索語では拾えず、実機では確かめていない。

<a id="iteration-1-record-2"></a>

### 判断: 読み取った意図を、現状と A/B/C へ当てる

#### 判断対象・必須条件・根拠

一案を選ぶためではなく、本人が反応する材料を作るために当てる。
そのため推奨と重みは置かない。
根拠は認識合わせ0への回答と、キャンバスの各ボードのソース（`Main`、`OptionA`、`OptionB`、`OptionC`）である。

#### 当てた結果

- 現状
    - 土曜から金曜を見る点は保つが、1画面に収まらない。
    - カード全面の色、左のバー、ラベルで時間帯の判別は強い。
    - 操作欄と評価の常時表示は本人の意図どおりである。ボタンは 28px である。
- A 献立リスト
    - 土曜から金曜が1画面に収まる。
    - 評価の常時表示を失っている。行は点数の表示だけで、評価するにはシートを開く。ここは本人の意図に反する。
    - 時間帯の判別は小さい印だけになり、現状より弱い。
- B 今日から
    - 毎日見る場面に最も強い。
    - 今日より前の日を一覧から落とすため、土曜から金曜を一つの計画として見る意図に反する。キャンバスは今日が土曜のため、この問題が見えていない。
    - 他の日の操作は未設計である。
- C 昼夜マス目
    - 土曜から金曜が1画面に収まり、列の位置と色で時間帯の判別が最も強い。
    - 評価の常時表示がない。操作は移動だけを作り、他は未設計である。
    - 「出社」が昼のマスを埋めるため、イベントと食事を分けたい意向とは逆向きに見える。
- 三案に共通
    - イベントを食事と別に表していない。キャンバスを作った時点で、この意向を知らなかった。

#### 前回の提示への影響

A を推奨した時の決め手は、昼夜の使い方を前提にしないことだった。
この決め手は評価の常時表示を見ていない。
A を推奨した判断は、そのままでは維持できない。
ただし行へ評価の操作を足せば解消する範囲であり、A の骨格を否定する根拠にはならない。

#### 確認していないこと

キャンバスの描画と操作は確認しておらず、当てた結果はソースの読解による。
どの意図を重く見るかは本人の判断であり、ここでは決めない。

## イテレーション2: 三案への反応から、意図を一つの一覧として言えるか

<a id="iteration-2-record-1"></a>

### 一般化: 三案を採らない理由に共通するものは何か

**成立した原則: 使う場面で必要な情報と操作の入口は、別の操作なしで見えている。全ての操作を出すという意味ではない。**

#### 起点caseと暫定原則

起点は二つの反応である。
A は「材料揃えるときとか、作るときに必要な情報が出てない」、B は「今日以外の情報が秘匿されている」である。
暫定原則を「使う場面で必要な情報は、操作なしで見えている」と置いた。

#### 異なるcaseと原則の修正

- 食事の追加ボタン
    - 情報ではなく操作の入口だが、本人は「テクニカルに隠されているとかじゃわからない」と述べた。
    - 暫定原則では扱えないため、対象を「情報と操作の入口」へ広げた。
- 操作欄の九つ前後の操作
    - 反例の候補である。全てを見せる原則なら、本人が避けたかった破綻へ戻る。
    - 本人は食事編集や削除を常時出すことを求めていない。そこで対象を「その場面で必要なもの」へ限定した。
- 評価
    - 「常時表示」と言っていたが、「たいてい今日食べたものについて起こる」と具体化された。
    - 場面で切ると、今日の食事には入口が必要で、他の日は不要かもしれないと説明できる。原則と矛盾しない。

#### 既確認caseへ戻した結果

- A: レシピ元が操作の先にあるため満たさない。キャンバスの A は `showSource` の既定が無効で、Tweaks で有効にすると行に出る。今日の評価の入口もない。
- B: 他の日のレシピ元がなく、食事のある日の追加ボタンがないため満たさない。
- C: レシピ元がなく、食事のあるマスに追加ボタンがないため満たさない。
- 現状: レシピ元、追加ボタン、評価の入口が見えており満たす。意図がないのは重い見た目のほうである。

#### 適用境界と未確認

次は原則だけでは決まらず、本人の回答がない。

- 料理コメントと食事コメント。現状の `MealCard` は表示する。キャンバスの三案は表示欄を作っておらず、サンプルにも入れていない。
- 他の日の評価の点数の表示。
- 区分アイコン。

### 調査: 「ワンタップ」と現状の評価の流れ

#### 問い・探索範囲・方法

本人の「ワンタップ」が現状で満たされているかを、`MealCard` と `EvaluateDish` のソース、`.steering/2026/202608/20260823-fix-dish-card-tap-copy-naming/design.md` で確かめた。

#### 見つかった事実

現状は、★のボタンで評価モーダルを開き、星を選び、「登録」を押して保存する。
入口までは1タップだが、完了までは3タップである。
本人の発言だけでは、どちらを指すかを確定できない。

レシピ元については、同じ design の元の依頼に、名前コピーを「レシピ元の料理名」の形にしたいとある。
レシピ元を料理の同一性の一部とする今回の発言と整合する。
現状の表示はレシピ元の名前を10文字で切り、ページは残している。

#### 言える範囲

提案では「ワンタップ」を評価を始めるまでと読み、違えば訂正を求める。
レシピ元の10文字の切り詰めが同一性の意図に足りるかは、見直し案で確かめる。
