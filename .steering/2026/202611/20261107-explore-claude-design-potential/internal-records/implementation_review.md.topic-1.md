# 内部検討記録: 論点1 — 確定案をコードへ移す時に、ボードの値をどう渡すか

**discussion:** [implementation_review.md](../implementation_review.md)

**論点:** 論点1

## 開始context

Phase 1〜6 で、Claude Design のキャンバスの確定案（`task-design-discussion.md` 論点16で受諾した確定案の page のボード）を週カレンダーのコードへ移した。
移した後、確定案と画面の間に、直す必要のある差が11点出た。
全て修正済みであり、本人の動作確認も済んでいる。

決める範囲は、この差の原因と、次に同じ差を防ぐために何をどこへ書くかである。
修正済みでも記録を省略しない、という tasklist の Documentation review の指示に従う。

開始時の既決条件は次のとおりである。

- `ui_design_management.md` は、正本をリポジトリに置き、Claude Design を作業場とする。決まったことはリポジトリへ戻す。
- グローバル CSS の前提は、実装の後の doc-enricher の提案から `global_css.md` を足して扱った。
- 論点17（`task-design-discussion.md`）: 写しは作り直しであり、作った時点から近似になる。

## イテレーション0: 差の原因と置き場所

根拠は `tasklist.md` の「確定案のボードとの差の記録」と、`design.md` の「週カレンダーの画面」、`tasklist.md` の各 Phase の入力である。

<a id="iteration-0-record-1"></a>

### 診断: 確定案と実装の差が11点出た

#### 期待との差と原因候補

期待は、移した後の画面が確定案のボードと一致することである。
実際は、直す必要のある差が11点出た。
原因候補は、確定案の値が実装へ渡っていないこと、グローバル CSS の前提、ボードと実物の作りの違い、検査の依頼の不足である。
差の記録の各項目の原因欄と、`design.md` と `tasklist.md` に値が書かれているかを照合した。

#### 原因を支持・反証する証拠

| 差 | 内容 | 原因 |
| --- | --- | --- |
| 差1 | 「今週」の幅が 40px | 値が渡っていない（`tasklist.md` が `h-11` とだけ書き、幅の下限を書いていなかった） |
| 差2 | レシピ元の文字色 | 値が渡っていない |
| 差3 | 食事コメントの薄さ | 値が渡っていない |
| 差5 | 期間ラベルが切れる（外側の余白と `<a>` の content-box） | グローバル CSS の前提と、値が渡っていない（外側の余白） |
| 差6 | 「評価する」の面と星 | 値が渡っていない |
| 差7 | 枠の行の印の色 | 値が渡っていない |
| 差8 | 料理名の行の配置 | 値が渡っていない |
| 差9 | 点数の色 | 値が渡っていない |
| 差10 | 操作欄の面 | 値が渡っていない |
| 差11 | 期間ラベルが 390px で切れる | ボードと実物の違い（文字幅） |
| 差12 | 区分アイコンが1行目とずれる | グローバル CSS の前提（`svg` が inline） |

`design.md` の「週カレンダーの画面」は、確定案を言葉で書き、細部を「確定案のボードのとおり」としていた。
差2、差3、差6〜10 の値は `design.md` にも `tasklist.md` にもなく、ボードにだけあった。
差1 は、`tasklist.md` が「今週」を `h-11` とだけ書き、ボードにある幅の下限を書いていなかった。
`tasklist.md` の各 Phase は、実装の入力にボードを挙げていなかった。

見つけた経路は、`visual-inspector` の検査（差1〜3）、私がボードと見比べたもの（差5〜10）、その再確認（差11、差12）である。
検査が差5〜10 を見落としたのは、私が検査へ渡したのが受け入れ基準の項目であり、ボードとの見比べを依頼していなかったためである。

#### 原因の分類

- 値が渡っていない: 8点（差1〜3、差6〜10）と、差5の一部。
- グローバル CSS の前提: 差5の一部、差12。`global_css.md` で扱い済み。
- ボードと実物の違い: 差11。移した後に実物を撮る以外に防ぎ方がない。

<a id="iteration-0-record-2"></a>

### 判断: 再発を防ぐ記述をどこへ置くか

#### 判断対象・必須条件・根拠

`ui_design_management.md` の「Claude Design を使う時の進め方」へ、移す手順と失敗例を足すことを推す。
決め手は、不足しているのが Claude Design のボードを見た目の仕様として使う時の、このリポジトリに固有の手順だからである。

必須条件は、次に Claude Design の確定案をコードへ移すセッションが、作業を始める前に読むことである。
比較した置き場所は、`ui_design_management.md`、task-design の skill、`design.md` だけの修正である。

#### 当てた結果

- `ui_design_management.md`: frontend を扱うセッションで `@` から読み込まれる。決まったことをリポジトリへ戻すことは定めているが、確定案の値を実装へどう渡すかは定めていない。不足と置き場所が一致する。
- task-design の skill: 既に「実装中に新しい判断が生まれない状態」を設計の完了としている。今回はその基準を満たさない `design.md` のまま実装へ進めたのであり、skill に問いが欠けていたのではない。plugin の修正提案には当たらない。
- `design.md` だけの修正: 今回の作業は終わっており、次の作業へ届かない。

手順は、値を書き出して渡すことと、移した後にボードと並べて確かめることを一つにする。
前者は値が渡っていない8点を、後者はボードと実物の違いと検査の見落としを防ぐ。
どちらか一方では移す手順として成り立たないため、一つの提案にする。

Tailwind v3 と v4 の色の値の違い（差13 と Design System の `rating-text`）は、作業場へ値をどう写すかという別の問いであり、この論点に含めない。

### 判断: 反映の後に、repository の文書へ残す知識がほかにあるか

#### 判断対象・必須条件・根拠

本人の受諾（「ok」）を受け、`ui_design_management.md` へ二つの行を足した。
この論点の提案自体が、原因を repository の知識の不足と分類した後の文書の修正案であり、doc-enricher の提案 review の一回に数える。
そのうえで、反映の後に残る候補がないかを Gate A〜G で確かめた。

#### 当てた結果

候補なしとした。

- グローバル CSS の前提による差は、`global_css.md` で扱い済みである（Gate G）。
- Tailwind v3 と v4 の色の値の違いは、作業場へ値をどう写すかという別の問いであり、論点2 で扱う。
