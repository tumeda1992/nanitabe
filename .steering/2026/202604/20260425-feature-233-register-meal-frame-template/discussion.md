# Discussion: 食事枠パターン登録・適用機能

## 論点1: `duration_days` フィールドの要否

**提起の背景:**
テンプレートの「日数」を DB カラムで明示的に持つか、エントリの `max(day_offset)` で暗黙的に管理するかという設計上の問題。末尾が空日のテンプレート（例: 7日テンプレートで日曜が空）を表現できるかどうかに影響する。

### 議論の変遷

#### 事象の記述
- Claude が `duration_days` カラムを追加することを推奨（末尾空日の表現に必要と判断）
- ユーザーが「末尾の空を登録させなきゃいいんじゃない？7日分で7日目が空なら6日で登録させればいいんだから」と指摘
- UX が辛くなったら後から考慮する方針

#### 根本原因 + 提案
- **根本原因**: 末尾が空の日を表現するユースケースは現時点では明確ではない。シンプルな設計を優先すべきだった
- **提案**: `duration_days` なし。テンプレート長 = `max(day_offset)` の暗黙管理を採用する

#### イテレーション1

##### 検証
- **観点:** ユーザーが「`day_offset=7` に `meal_frame_id=NULL` を入れれば表現できるのでは」と再提起
- **弱点（NULL アプローチ）:**
  - `meal_type` が宙に浮く。「夜が空」なのか「その日全体が空」なのかエントリ1行では表現できない
  - 1日2枠以上ある場合（朝・夜どちらも枠あり）にどの数だけ NULL を入れるか曖昧になる
  - nullable カラムが増える
  - テーブルに「データ（フレーム割り当て）」と「構造の宣言（日が空）」が混在する

##### 修正先の判断
- **提案レベル**: NULL は代替案として機能しない。`duration_days` か `max(day_offset)` のどちらかが正しい

##### 決定（ユーザー確認済み）
- **c) max(day_offset) のみ** を採用（当初の方針を維持）
- 理由: nullable カラムを増やしたくない。1日2枠以上あるとレコードの形が複雑になる

**決定:** `duration_days` カラムなし。テンプレート長 = そのテンプレートが持つエントリの `max(day_offset)` とする。末尾空日のサポートは今回スコープ外。

**ネクストアクション:** design.md のデータモデルに反映する（設計はすでにこの方針で記載済み）

## 論点2: テンプレート適用のエントリポイント（どこから適用するか）

**提起の背景:**
テンプレートを「テンプレート一覧ページ（別ページ）から適用」か「カレンダーの + ボタンから適用」かという UX 設計上の問題。

### 議論の変遷

#### 事象の記述
- Claude が a) テンプレート一覧ページから適用 を推奨（実装シンプル）
- ユーザーが「体験としてはbで作りたい」と指摘
- 理由: 日付についてはカレンダーしか見ない。別ページで既存日付を見返して確認するのが面倒

#### 根本原因 + 提案
- **根本原因**: テンプレート適用は「日付を見ながら開始日を決める」行為であり、カレンダーが日付コンテキストを提供する唯一の画面である。別ページに移動すると日付確認が不便になる
- **提案**: カレンダーの `+` ボタンに「テンプレート適用」を 3rd オプションとして追加する（b）。テンプレート一覧ページからの適用は補完的に追加してもよい

**決定:** b) カレンダーの `+` ボタンから適用を主とする。クリックした日が開始日のデフォルト。テンプレート一覧からの適用は補完（SHOULD）。

**ネクストアクション:** design.md の操作フロー・変更点一覧に反映する

## 論点3: テンプレート削除時のエントリ扱い

**提起の背景:**
テンプレートを削除するとき `meal_frame_template_entries`（テンプレートの構成）と、適用済みの `meal_frame_entries`（カレンダーエントリ）をどう扱うかという設計の問題。

### 議論の変遷

#### 事象の記述
- Claude が「cascade delete か削除ブロックか」を聞いた
- ユーザーが「登録したいのはエントリで、テンプレートは一括登録のための存在」と本質的な観点を示した
- 「履歴として別テーブルでエントリとテンプレートを関連付けてもいいが、それがエントリに影響を与えてはいけない」

#### 根本原因 + 提案
- **根本原因**: テンプレートと適用済みエントリの関係を混同していた。テンプレートは「道具」であり、適用によって生成された `meal_frame_entries` は道具と独立した実態である
- **提案**:
  - `meal_frame_template_entries`（テンプレートの構成定義）→ テンプレート削除時に cascade delete（テンプレートと一体）
  - 適用済みの `meal_frame_entries`（カレンダーエントリ）→ テンプレート削除の影響を受けない（独立して存在）
  - 適用時の履歴テーブル（どのテンプレートから生成されたか）→ 初期 MVP ではなし

**決定:** テンプレート削除時 → `meal_frame_template_entries` は cascade delete。適用済みの `meal_frame_entries` は影響なし。履歴テーブルは今回スコープ外。

**ネクストアクション:** design.md のデータモデル・リスクセクションに反映する

## 論点4: テンプレート登録の API 設計（N+1 呼び出し問題）

**提起の背景:**
操作フロー ケース1 で「`addMealFrameTemplate` を1回 → `addMealFrameTemplateEntry` を N回」と設計していた。フロントエンドが API を複数回呼ぶ形になっており、ユーザーから指摘を受けた。

### 議論の変遷

#### 事象の記述
- design.md ケース1 の⑧⑨で、フロントエンドがテンプレート作成とエントリ作成を別々の mutation で複数回呼ぶ形になっていた
- ユーザーが「バックエンドにテンプレート登録のエンドポイントを用意して1回だけ呼ぶ形にしたい。センス悪い」と指摘

#### 原因の追跡
- なぜ: テンプレートとエントリを別集約として捉え、個別 mutation をそれぞれ設計した
- なぜ: フロントエンドがオーケストレーションを担う設計になってしまった
- なぜ: フロントエンドの責務ではないうえ、mutation をまたいだ `ActiveRecord::Base.transaction` が機能しないため、途中失敗でテンプレートだけ作られエントリが欠ける部分適用が起きる

#### 根本原因 + 提案
- **根本原因**: 「テンプレートとそのエントリは一体として登録・更新される」という不変条件を、API 設計に反映できていなかった
- **提案**:
  - `addMealFrameTemplate`: `name` + `entries[]` を受け取り、resolver が1トランザクションで template と全エントリを作成する
  - `updateMealFrameTemplate`: `id` + `name` + `entries[]` を受け取り、resolver が1トランザクションで name 更新 + 全エントリ置換する
  - `addMealFrameTemplateEntry` / `removeMealFrameTemplateEntry`: 主フローでは不要（将来のインクリメンタル編集UX向けに残してもよいが、MVP スコープからは外す）

**決定:** `addMealFrameTemplate(name, entries[])` / `updateMealFrameTemplate(id, name, entries[])` の一括バッチ設計を採用。resolver が1トランザクションで作成・置換する。個別エントリ mutation は MVP スコープ外。

**ネクストアクション:** design.md の操作フロー（ケース1・ケース3）・3-3 クラス・API 設計・変更点一覧を修正する

## 論点5: モジュール階層設計（FrameEntry / FrameTemplate の配置）

**提起の背景:**
design.md の 3-3 クラス・API 設計で `Meal::FrameTemplate::Root` / `Meal::FrameTemplateEntry::Root` を `Meal::` 直下に置く設計にしていた。ユーザーから「`Meal::` 直下に `Frame`, `FrameEntry`, `FrameTemplate`, `FrameTemplateEntry` の4兄弟が並ぶのは嫌」と指摘を受けた。また、既存の `FrameEntry` も `Meal::` 直下にあることを見落としていたことも判明した。

### 議論の変遷

#### 事象の記述
- design.md が `Meal::FrameTemplate::Root` / `Meal::FrameTemplateEntry::Root` を `Meal::` 直下に配置していた
- ユーザーが「`FrameTemplate` と `FrameTemplateEntry` が `Meal::` 直下に並ぶのが嫌。同じ括りで同じディレクトリに収めたい」と指摘
- 「`FrameEntry` と `Frame` も1セットだし、`Frame` と `FrameTemplate` も近い」という関係性の整理
- さらに「`template_entry` を `template` 配下にしたい」という追加の意見

#### 根本原因 + 提案
- **根本原因**: `Frame` に関連するすべての概念（枠マスタ・カレンダーエントリ・テンプレート・テンプレートエントリ）が `Meal::` 直下にフラットに並んでいた。概念間の親子・兄弟関係がディレクトリ構造に反映されていなかった
- **提案**: `Frame` を親として、関連する全概念を `Meal::Frame::` 傘下に集約する

```
Meal::Frame::Root                      (枠マスタ)
Meal::Frame::Entry::Root               (カレンダー枠エントリ。既存 FrameEntry をリネーム)
Meal::Frame::Template::Root            (テンプレート)
Meal::Frame::Template::Entry::Root     (テンプレートエントリ)
```

ディレクトリ:
```
meal/frame/
  root.rb
  entry/          ← 既存 meal/frame_entry/ を移動
  template/
    root.rb
    entry/        ← TemplateEntry は Template 配下
```

**決定:** 上記モジュール階層を採用する。既存の `Meal::FrameEntry::*` → `Meal::Frame::Entry::*` へのリネーム・ディレクトリ移動もこの steering のスコープに含める。

※ この時点ではコンセプト名を「テンプレート」として議論していたが、その後の論点6でコンセプト名が「パターン」に変更された。したがって最終的なクラス名は `Meal::Frame::Pattern::Root` / `Meal::Frame::Pattern::Entry::Root`、ディレクトリは `meal/frame/pattern/` となる。

**ネクストアクション:** design.md の 3-3 クラス・API 設計・変更点一覧を修正する（修正済み）

## 論点6: コンセプト命名（テンプレート vs パターン）

**提起の背景:**
design.md の 3-3 クラス・API 設計で「テンプレート」という名前を使っていたが、カレンダーの `+` ボタンセレクタの表記を検討する中で「テンプレートという言葉自体を議論していなかった」とユーザーが指摘。命名の妥当性を議論していなかった設計上の問題。

### 議論の変遷

#### 事象の記述
- セレクタラベル検討中にユーザーが「テンプレートという言葉自体はいいか議論してなかった」と問題提起
- Claude が「このテーブルがどんな進化をしそうか」を問い、実態の想定から命名の本質を探ることを提案
- ユーザーが「枠に閉じるかな。サイクル（繰り返し）はありえる。ただ Routine は繰り返しを前提としてしまっていて、そうとも限らない」と進化の方向性を示した
- Claude が「テンプレート」を推奨しようとしたが、ユーザーから「勝手になに結論決めてるの？パターンっていうのが近くない？」と指摘

#### 原因の追跡
- なぜ: Claude が「テンプレート」という名前を利用目的（型として使う）から導いた
- なぜ: ドメインの本質（複数日分の枠配置の「配置パターン」）から命名していなかった
- なぜ: 「テンプレート」は「それを使ってなにかを作る」という利用法の観点の命名。「パターン」はデータ構造の本質を指す

#### 根本原因 + 提案
- **根本原因**: 命名をドメインの本質（何であるか）ではなく、利用法（何に使うか）から行ってしまった
- **提案**: 「パターン」を採用する
  - 「パターン」はデータの実態（複数日の枠の配置構造）を指す
  - 「このパターンを繰り返す」という将来的なサイクル機能とも整合性が高い
  - 「パターンを適用する」という日本語が自然に成立する
  - 「テンプレート」より「パターン」が本質に近いという直感が正しい

**決定:** コンセプト名を「パターン」に決定。すべてのクラス名・テーブル名・mutation 名を Template → Pattern にリネームする。以降の 論点1〜5 では「テンプレート」が使われているが、最終的な名前はすべて「パターン」である。

**ネクストアクション:** design.md を全面更新（Template → Pattern）、discussion.md に記録

## 論点7: UI セレクタラベル（枠パターン vs 枠パターン適用）

**提起の背景:**
カレンダーの `+` ボタンのセレクタに「食事 / 枠 / ???」と並べるとき、3つ目の選択肢のラベルをどうするか。コンセプト名「パターン」が確定した後、ラベルをどう表現するかという UI 設計上の問題。

### 議論の変遷

#### 事象の記述
- 「枠パターン」というラベルを最初に合意
- ユーザーが「セレクタに並ぶのが『食事/枠』で『枠パターン』となると、枠パターン自体の登録に見えてしまう」と指摘
- 「食事 → 食事を登録、枠 → 枠を登録、枠パターン → 枠パターンを登録？」という読みになってしまう
- 「枠パターン適用」であれば「パターンを選んで適用する操作に入る」と明示できる

#### 根本原因 + 提案
- **根本原因**: 「食事」「枠」はともに noun（登録する対象）だが、「パターン適用」は action（行為）。セレクタの並びで noun と混在させると意味がずれる。ただし既存の「食事」「枠」も「食事を登録」「枠を登録」という行為に対応しており、名詞から行為を想起させるパターンとして機能している。問題は「枠パターン」だと「パターン自体を新規作成する」なのか「パターンを選んで適用する」なのかが曖昧になること
- **提案**: 「枠パターン適用」を採用する
  - 「適用」を明示することで「この選択肢はパターンを当てはめる操作」と伝わる
  - 「食事」「枠」との非対称（名詞 vs 名詞+動詞）は許容。意味の明確さを優先する

**決定:** セレクタラベルは「枠パターン適用」に決定。

**ネクストアクション:** design.md の操作フロー・3-3 クラス・API 設計を「枠パターン適用」に更新

## 論点8: 新概念追加時のモジュール階層設計（思考停止フラット配置）

### 議論の変遷

#### 事象の記述
- `Meal::Frame::Pattern::Root` を設計する際、既存の `Meal::Frame::Root` / `Meal::FrameEntry::Root` と並列に `Meal::FramePattern::Root` として `Meal::` 直下に配置する提案をした
- ユーザーが「`Frame`, `FrameEntry`, `FramePattern`, `FramePatternEntry` の4兄弟が `Meal::` 直下に並ぶのが嫌」と指摘
- 指摘を受けて初めて「Pattern は Frame の文脈でのみ意味を持つ」という判断を行い、`Meal::Frame::Pattern::*` の階層に修正した

#### 原因の追跡
- なぜ: 新概念を追加するとき、「この概念は既存概念との関係でどこに属するか？」を先に問わなかった
- なぜ: 既存の `application_architecture.md` に「このエンティティは既存のドメイン概念の文脈を外れても意味を持つか？」という判断基準があったが、設計提案時に適用できていなかった
- なぜ: 設計の流れの中でクラス名を書き出す際に、「どこに置くか」ではなく「何を作るか」に注意が向いていた

#### 根本原因 + 提案
- **根本原因**: 新しい概念を追加するとき「既存概念との階層関係は何か？」を問わずに、デフォルトでトップレベル（`Meal::` 直下）に並べてしまった
- **提案**: 新概念の配置を提案する前に「このエンティティは、既存のドメイン概念の文脈を外れても意味を持つか？」（`application_architecture.md` の原則）を必ず問う
  - `Meal::Frame::Pattern::Root` は `Frame` の文脈を外れて意味を持たない → `Meal::Frame::` 傘下
  - フロントエンドの `src/features/` も同様: `meal/frame/pattern/` が正しい。`features/mealFramePattern/` をトップに置くのは誤り

**決定:** CLAUDE.md に「モジュール・ディレクトリ配置提案前の問い」として追記することを提案する（合意後）。

## 論点9: 命名の根拠（現状整合性ベース vs 本質ベース）

**提起の背景:** 論点6・7の命名議論で、Claude が「テンプレート」という名前を推奨する際に「現在の他の命名との整合性」を根拠の一つとして挙げた。ユーザーから「テーブルは今後も息づくものにかかわらず、現状での整合性を見て名付けをするのは悪手」と指摘を受けた。命名の根拠として何を優先すべきかという問題。

### 議論の変遷

#### 事象の記述
- 命名議論の中で Claude が「テンプレート」を推奨する理由として、既存コードとの整合性（命名の一貫性）に触れた
- ユーザーが「本質を見出すための例として今回進化の可能性を提案させた」が、Claude はその問いかけに対して本質から命名せず現状整合性に傾いた
- 「テーブルは今後も息づくものにかかわらず、現状での整合性を見て名付けをするのは悪手」と指摘された

#### 原因の追跡
- なぜ: 「現在のコード・テーブルとの整合性」を命名の根拠として使ってしまった
- なぜ: 「整合性がある = 違和感が少ない = よい命名」という短絡が起きた
- なぜ: テーブル名・クラス名・モジュール名は変更コストが高く長期間存在するという性質を、命名の判断に組み込めていなかった
- なぜ: 命名の正しい根拠（「そのエンティティが本質的に何であるか」）ではなく、表面的な整合性（「現在の他の命名との一致」）を優先した

#### 根本原因 + 提案
- **根本原因**: 命名を「このエンティティは本質的に何であるか？」から行うべきだが、「現在の他の命名との整合性」という外部基準から行ってしまった
- **提案**: 命名は「このエンティティ・テーブルは本質的に何であるか？（何をするものか・何を表すものか）」から問う
  - 現状整合性は根拠にならない。テーブルは変更コストが高く、現状の命名パターンより本質の方が長く正しい
  - 「テンプレート」は「型として使うもの」という用途から来た命名。「パターン」は「複数日の枠配置の構造」という本質から来た命名
  - テーブルは長生きする。現状コードとの整合性に基づいた命名は、将来の認識ズレを固定化する

**決定:** CLAUDE.md に「命名は本質から行う（現状整合性は根拠にならない）」として追記することを提案する（合意後）。

**ネクストアクション:** CLAUDE.md 追記の提案（合意後適用）

## 論点10: visual-inspector で確認できなかったのにタスクを完了とした

**提起の背景:**
implementation_review.md に記録された Bug 1（requireFetchedData 誤用によるセレクタ空）の振り返りで、この bug が開発時の visual-inspector 確認で発覚しなかった理由を掘り下げた。tasklist-executor がデータのない状態でスクリーンショットを撮り「データ未登録のため空」と記録して ✅ にしてしまっていたことが問題の根本にある。

### 議論の変遷

#### 事象の記述
- Phase 2 の visual-inspector 確認で、meal_frame データが DB に存在しない状態でスクリーンショットを撮った
- 「データ未登録のため空」と記録して確認完了（✅）とした
- 実際には `requireFetchedData: false` によってクエリ自体がスキップされており、データを登録しても空になる状態だった
- ユーザー動作確認（Phase 9）で初めて発覚した

#### 原因の追跡
- なぜ: データがない状態で「データ未登録」と「クエリスキップ」を区別できないまま確認完了とした
- なぜ: データがなければ自分で作成してから確認することを選ばなかった
- なぜ: 「確認しようとした」ことを「確認できた」とみなした。確認できていない＝完了していない、という原則が守られていなかった

#### 根本原因 + 提案
- **根本原因**: 確認ステップで「確認の試み」と「確認の完了」を混同した。データがない・環境が整っていないという理由で確認できなかった場合、タスクを完了とすることは禁止
- **提案**:
  1. データがなければ自分で作成して確認する（フォーム入力・DB 直接挿入など）
  2. 本当に確認できない場合はユーザーに報告してから次へ進む（タスク途中でも、他タスクをまとめて終えた後でも）
  3. 確認できていない状態で ✅ にすることは禁止

**決定:** tasklist-executor.md に上記ルールを追記（適用済み）。

## 論点11: CLAUDE.md への追記判断の誤り（「普遍的」の乱用と合意なき書き換え）

**提起の背景:**
論点10の再発防止として「確認できていないのに完了とマークしない」を CLAUDE.md に追記しようとした。その際、「普遍的だから CLAUDE.md でよい」という判断で合意を取らずに書き換えようとした。さらに、CLAUDE.md の「CLAUDE.md に書くこと・書かないこと」セクションの判断基準を自分で適用できていなかった。

### 議論の変遷

#### 事象の記述
- 論点10の対処として CLAUDE.md への追記を提案
- 「普遍的だから」という理由で CLAUDE.md が適切と判断した
- ユーザーから「UI 要素の話をアーキテクチャ資料でなく CLAUDE.md に書こうとしていた（別論点でも）。普遍的という言葉ですんなり CLAUDE.md に入れすぎ」と指摘
- 正しい判断の問い「テストを書くときも・設計するときも・レビューするときも前提なしに当てはまるか？」に当てはめると → **No**（tasklist 実行中・visual 確認という条件付き）
- さらに合意なく CLAUDE.md を書き換えようとしてユーザーに止められた

#### 原因の追跡
- なぜ: 「普遍的」「文脈を問わない」という言葉で自分を正当化し、判断の問いを実際に適用しなかった
- なぜ: 「tasklist 実行中」「visual 確認のとき」という条件があることに気づいていたが、それを「条件あり＝CLAUDE.md 不適切」と接続できなかった
- なぜ: 合意なく CLAUDE.md を書き換えようとした。CLAUDE.md 自身に「修正前の方針合意」が書いてあるにもかかわらず

#### 根本原因 + 提案
- **根本原因1（判断の問いの形骸化）**: 「普遍的だから CLAUDE.md」という判断フローが短絡になっており、実際に具体的なタスクに当てはめる検算を省いた
- **根本原因2（合意プロセスの無視）**: CLAUDE.md への追記は他のファイルと同様に合意が必要。CLAUDE.md が特別扱いされ、合意なく書き換えることを許容してしまった
- **提案**:
  - CLAUDE.md の「やってしまいがちな行動」に「普遍的という言葉で判断の問いを省く」パターンを追記する（合意後適用）
  - 正しい検算: 具体的なタスク（設計・テスト作成・コードレビュー）で当てはまるか一つひとつ確認する

**決定:** CLAUDE.md の「CLAUDE.md に書くこと・書かないこと」セクションへの追記を提案する（ユーザー合意後に適用）。

**ネクストアクション:** ユーザーに CLAUDE.md 追記内容の合意を得てから適用する
