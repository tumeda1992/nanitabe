# Discussion: フェーズ2 食事への割り当て

## 論点1: fillMealFrameEntry の mutation 設計

**提起の背景:** ロードマップに「fillMealFrameEntry mutation 追加（Meal 作成後に resolver がオーケストレーション）」と記載があり、この記述をそのまま「fillMealFrameEntry の resolver 内で Meal 作成 + 紐付けを行う独立 mutation」と解釈して設計を始めた。しかしロードマップ作成時点で「出来上がるものの具体的な姿」を詰めていなかったため、UX の意図と乖離した設計になっていた。

**議論の変遷:**
- [前提] fillMealFrameEntry(meal_frame_entry_id, dish_id) という独立 mutation を設計
  - resolver 内で Meal 作成 + FillWithMealCommand をオーケストレーション
  - フロントエンドは1回の mutation 呼び出しで完結する想定
- [問題] addMealWithNewDish / addMealWithNewDishAndNewSource 等の全バリアントを fillMealFrameEntry に重複実装するのは現実的でない
  - → フロントエンドで addMeal → fillMealFrameEntry の2回呼び出し案に変更
  - → しかしこれではトランザクションが保証できない
- [ユーザー指摘] 「AddMeal系の引数にframe_entryのidを渡すんじゃないの？」
- [変化点] 設計の根幹が変わる。addMeal 系に optional frame_entry_id を追加し、resolver が FillWithMealCommand を呼ぶのが正しい
- [ユーザー確認] fillMealFrameEntry 独立 mutation は不要

**決定:** fillMealFrameEntry 独立 mutation は作らない。`addMeal` / `addMealWithNewDish` / `addMealWithNewDishAndNewSource` に optional `frame_entry_id: Int` を追加し、resolver が Meal 作成後に FillWithMealCommand を呼ぶ。

**決定理由:** トランザクションが一本化できる。既存 addMeal バリアントをそのまま活かせる。フロントエンドの変更最小限。

## 論点2: FrameCard クリック時の UI

**提起の背景:** FrameCard は「料理を枠に割り当てる」操作の起点。この文脈を「割り当て操作」として解釈すると専用の料理選択 UI が適切に見えるが、実際のメンタルモデルと乖離していた。

**議論の変遷:**
- [前提] FrameCard クリック → 専用「料理選択」コンポーネント（料理検索 + 選択 + 登録ボタン）
  - pros: 枠割り当てに特化したシンプル UI
  - cons: 新コンポーネントが必要
- [別案] 既存 AddMeal フォームを流用（date/meal_type を pre-fill）
  - pros: 既存コンポーネント再利用
  - cons: コメント入力など不要なフィールドも見える？ → これが疑問点だった
- [ユーザー指摘] 「食事の登録がメイン、枠はその補助。コメントも入力するし、料理がなかったら登録もする」
- [変化点] 「割り当て操作」ではなく「食事登録（枠 pre-fill 付き）」というメンタルモデルに転換。「コメントなど不要」というのは誤った前提だった

**決定:** 既存の AddMeal フォームを流用。`frameEntryId` を optional prop として追加するだけ。

**決定理由:** UX 的に正しい（食事登録の全機能が使える）。onAddSucceeded の interface 変更不要。フロントエンドの変更最小限。

## 論点3: ロードマップ時点での「出来上がるものの認識合わせ」の必要性（プロセス改善）

**提起の背景:** 論点1・2の設計の迷走は、ロードマップを作った時点で「出来上がるものの具体的な姿（UX・mutation の引数・データフロー）」を詰めていなかったことに由来する。ロードマップは「個々のタスクの進め方は後回しでいい」が、「出来上がるものの認識合わせはそこで詰めておくべき」というフィードバックがあった。

**議論の変遷:**
- [現状] ロードマップのフェーズ記述は DoD とタスク概要のみ。具体的な mutation 引数・フロントエンドのフローは「子 steering で詰める」前提
- [問題] mutation の引数・UX のメンタルモデルは、子 steering で詰め始めた段階で初めて認識のズレが表面化した。結果として設計の根幹を2回書き直すことになった
- [ユーザー指摘] 「ロードマップで個々のタスクの進め方は後回しでもいいけど、出来上がるものの認識合わせはそこで詰めとかなきゃだめ」

**決定:** steering スキルへの改善提案として記録する（後述）。

**決定理由:** 「出来上がるもの」の認識合わせは後から覆すコストが高い。mutation の引数・UX フローはロードマップ段階で最低限揃えておくべき情報。

### 改善内容（steering SKILL.md に反映済み）

**根本原因の特定過程:**
- 最初の提案「ロードマップの各フェーズに mutation 引数を書く」→ ユーザーに却下（実装詳細はロードマップに書くものではない）
- 次の提案「メンタルモデルを含める」→ ユーザーに却下（抽象的すぎて再現できない）
- 「フロントエンドが何を何回呼ぶかの操作フローを書く」→ ユーザー指摘「バックエンドも」
- 「各フェーズごとに書く」→ ユーザー指摘「design.md に全部網羅したものを作らなかったことが問題」
- 「ロードマップに design.md を追加する」→ ユーザー指摘「ロードマップのところに design.md はあるよ」
- 実際の design.md を読むと: データ例はあった。操作フロー（誰が何を何回呼ぶか）がなかった

**本当の根本原因:**
design.md が「完成後の姿」ではなく「変更点の列挙」になっていた。データ例はあっても「ユーザー操作→フロントエンド呼び出し→バックエンドのクラス・メソッド→データ変化」の一気通貫したフローがなく、「誰が何を何回呼ぶか」の認識が揃わなかった。

**決定:** steering SKILL.md の design.md 作成ガイドライン（step 3）に「完成後の姿（MUST）」セクションを追加。ユーザー操作からデータ変化までの番号付きステップフローを必須とする。

## 論点4: 実装後フィードバックの収集・整理プロセス（プロセス改善）

**提起の背景:** 実装完了後のレビューで複数の漏れ・追加要件が判明した。これをどう収集・整理するか、また既存 tasklist との関係をどう扱うかの方針が未定義だった。

**議論の変遷:**
- [疑問] 追加要件を既存 tasklist に追記するか、feedback ファイルを作って再設計するかで迷った
- [決定] feedback ファイル（`implementation_review.md`）を作り、フィードバック収集 → 認識合わせ → 設計 → タスク整理 の4ステップを踏む
- [命名の問題] 最初に `feedback.md` と命名したが、`discussion.md`（実装前の設計議論）と無文脈では区別がつかない
- [命名決定] `implementation_review.md`（実装後レビュー）に改名
- [tasklist 追記の方針] 最初「完了済み tasklist への追記は意味的汚染」と判断したが、ユーザー指摘で誤りと気づく。tasklist は機能を完成させるためのチェックリストであり、追加要件が判明しても同じ機能の完成を目指す以上、tasklist は生き続ける

**決定:**
- 実装後フィードバックは `implementation_review.md` に集約する（`discussion.md` は実装前、`implementation_review.md` は実装後）
- フィードバック収集 → 認識合わせ → 設計 → タスク整理 の順で進める
- 整理後のタスクは既存 tasklist.md に追記する

**決定理由:** 機能が「完成」するまで tasklist は生きた文書として扱うのが正しい。feedback ファイルで整理してから追記することで、場当たり的な継ぎ足しを防ぐ。

### 改善内容（steering SKILL.md に反映済み）
- 成果物セクションに `implementation_review.md` を追加（`discussion.md` との違いを明記）
- step 11 として「実装完了後レビュー」フローを追加

## 論点5: 設計セクションの書き方（設計 = 変更点列挙ではない）

**提起の背景:** `implementation_review.md` の設計セクションを書いた際、「変更箇所: ○○ファイルの△△を修正」という形式で書いてしまい、ユーザーから指摘を受けた。

**議論の変遷:**
- [問題のある行動] 設計セクションを変更点の列挙（どのファイルに何を変えるか）で書いた
- [ユーザー指摘] 「これじゃタスクリストじゃん。設計というのは、完成後のコードと現状のギャップを埋める進め方の認識合意なんだよ」
- [変化点] 設計 = 「完成後の世界でユーザーが何を体験できるか」を操作フローで示すもの。変更点の列挙は補足（タスク整理で行うもの）

**決定:** 設計セクションは操作フロー中心で書く。steering SKILL.md の方針と同じ原則が implementation_review.md の設計にも適用される。

**決定理由:** 「変更点列挙」は「何を変えるか」の視点。設計が目指すのは「完成後の世界の認識合わせ」。認識が合って初めてタスクに落とせる。

## 論点6: implementation_review.md の見出し構造とその意図

**提起の背景:** `implementation_review.md` を新設するにあたり、4つの見出し（フィードバック収集・認識合わせ・設計・タスク整理）を設けたが、各セクションに何をどう書くかの意図が言語化されていなかった。セクションの意図が不明確だと、誤った書き方が繰り返される。

**議論の変遷:**
- [問題] 認識合わせを「1行サマリー」で書いてしまうリスクがある。数往復の議論も「〜で確定」の1行になってしまうと、なぜそうなったかが揮発する
- [ユーザー指摘] 論点は discussion.md と同じ形式にしないと、数往復の議論が1行にまとめられてしまう恐れがある
- [問題] 設計セクションを変更点の列挙（タスクリスト）で書いてしまうリスクがある（論点5参照）
- [ユーザー指摘] 設計はタスクリストにならないよう steering の design の思想を参考にする

**決定:** 各セクションの意図と書き方は以下の通り

| セクション | 意図 | 書き方 |
|---|---|---|
| 1. フィードバック収集 | ユーザーの言葉をそのまま残す。解釈・サマリー禁止 | 言われた通りに箇条書き転記 |
| 2. 認識合わせ | フィードバックの意図・前提・決定理由を揃える | discussion.md と同じ「論点N」形式（提起の背景・議論の変遷・決定・決定理由） |
| 3. 設計 | 完成後の姿を示し、現状とのギャップを埋める進め方を合意する | steering の design と同じ思想。操作フロー中心。変更点の列挙（タスクリスト）にしない |
| 4. タスク整理 | 設計の認識が合った後に実装ステップに落とす | DoD 付きフェーズ構成。合意後に既存 tasklist.md に追記する |

**決定理由:**
- フィードバック収集をサマリーにすると「ユーザーが言った意図」が変質する。まず原文保存が最優先
- 認識合わせは discussion.md と同じ形式にすることで、議論の変遷（初期認識 → 覆り → 決定）が残り、同じ議論の再発を防げる
- 設計を変更点列挙にすると認識合わせではなく作業指示になる。「完成後の世界」を先に揃えないとタスクの粒度・順序が正しく決まらない

## 論点7: 参照すべき既存仕様の洗い出し不足（振り返り・未決）

**提起の背景:** FB-4（枠経由 DishCard のデザインが v0 と異なる）は、参照すべき仕様が存在していたにもかかわらず、設計・実装前に確認していなかったことで発生した。

- なぜ: 参照しようという発想がなかった
- なぜ: feature-234 を「新機能の設計」として捉えており「feature-64 の延長」として捉えていなかった
- なぜ: 「新しく追加するもの = 既存制約なし」という暗黙の前提があった

#### 根本原因₀ + 提案₀
- **根本原因₀**: 「新規追加なら既存設計から自由」という誤った前提。変更・拡張する対象に既存の設計・合意が存在するかを確認する習慣がない
- **提案₀**:
  - 総論: steering SKILL.md の設計フェーズに既存仕様確認ステップを追加する

- **提案レベル**: 根本原因の定式化は正しい。問いの設計が具体的な成果物に縛られすぎていた

##### 根本原因₁ + 提案₁
- **根本原因₁**: 変わらず
- **変更点**: 提案₀の3問（design.md・デザイン仕様・ドメインモデルという成果物指定）を、「対象を列挙して積極的に探す」という対象指定に抽象化した

- **観点**: 「対象を列挙して探す」ステップは変更・拡張対象が確定していることを前提とする

  - この状態で「変更・拡張する対象を列挙する」ステップを実行すると、対象が定まっていないため形式的に「なし」で通過するか後回しにされる

  - 「設計フェーズ開始時の一括確認」として定式化すると対象が未確定なため機能しない
  - 習慣が発動すべきタイミングは「設計開始時」ではなく「変更・拡張対象が確定した瞬間」

- **根本原因₂**: 「何かを変更・拡張すると決定する」という行為に既存仕様確認が紐づいていなかった。変更・拡張対象が確定した瞬間に既存仕様を探すというトリガー型の習慣がなかった
- **変更点**: 提案₁の「設計フェーズ内に確認ステップを設ける」を、「変更・拡張対象が確定した瞬間に確認する」というトリガー型に変更した。設計初期に対象が未確定なケースでは一括確認ステップが形式的通過になるため
- **提案₂（現時点）**:
  - 総論: steering SKILL.md の各設計判断ステップに既存仕様確認をトリガー型で組み込む
  - 各論:
    - steering SKILL.md の各設計判断ステップに「この変更・拡張対象に既存の設計・合意が存在するか積極的に調べる」注記を追加する
    - design.md テンプレートに `## 前提とする既存仕様`（調べた仕様の要点まで記載）を追加する（変わらず）

#### イテレーション3

##### 検証
- **観点（ユーザー指摘）**: 「抽象化されすぎて、どこでも適用されないような提案になっている。初見の人にルールが伝わらない。具体と抽象の往復は、抽象を書きながらも具体で地に足をつけることが必要」

##### 根本原因₃ + 提案₃
- **根本原因₃**: 変わらず
- **変更点**:
  - 「探す」だけでなく「見つかったら従う・感覚で上書きしない」を追加した
  - 各論をルール本文とし、具体例を「適用例」として補足する形にした（提案₂では「積極的に調べる」という1行だけだった）
- **提案₃（現時点）**:
  - 総論: 変更・拡張対象が確定したタイミングで、その対象の既存仕様を探し、存在する場合はそれに従う

## [メモ] 論点10 議論中に発生した進め方の問題

- SKILL.md / CLAUDE.md（行動ルール定義ファイル）と discussion.md（会話の記録ファイル）では性質が異なるが、hook は区別していない

  - `.claude/skills/**` / `CLAUDE.md`: 現行の厳格チェック（フル LLM レビュー）を維持
  - `.steering/**/discussion.md`: `claude_announced_file` のみ（ファイルが会話に出ていれば通過）

  - 抽象と具体のふり幅を往復しており、抽象と具体を同時に持つ形になっていなかった

##### 根本原因₅ + 提案₅

- **変更点**: 各論の要件として「ルール本文 + 適用例（補足）」の形式を追加した。具体例を各論の本文にしないこと、抽象ルールと具体例はセットで示すことを明記する

- FB-9: mutation 完了後の refetch が必要なことを設計時に見落とした

- なぜ: 設計時の操作フローが「作成/登録」ケースのみで完結しており、削除・更新・画面反映が設計対象になっていなかった

- **提案₀**:
  - 総論: design.md テンプレートの操作フローセクションに CRUD ライフサイクルの確認を組み込む

**決定:** 提案₀で合意

## 論点9: UX 細部が設計段階で詰められていなかった（振り返り）

**提起の背景:** FB-1・FB-2・FB-6・FB-7 は「機能として動く」ことを目標にして、入力方式・バリデーション挙動・操作感の細部を設計段階で確認していなかったことで発生した。

- FB-7: バックエンドが nullable なのにフロントで必須バリデーションをかけていた

#### 原因の追跡
- なぜ: FB-2/6 は操作フローが「機能が動く」レベルで止まっており、「ユーザーが何回タップするか・どう感じるか」まで踏み込んでいなかった

- なぜ: design.md の操作フロー記載に「ユーザー視点の操作手数」と「バックエンド制約との整合」を確認するきっかけがなかった

#### 根本原因₀ + 提案₀

- **提案₀**:

    - ルール: フロントのバリデーション設定はバックエンドの nullable/required 定義と照合して記載する
