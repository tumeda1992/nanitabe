# 要件ドキュメント

## はじめに

Vercel v0 で作成したカレンダー画面デザインを、本番フロントエンドに段階的に移行する。
「でかすぎるタスクを1段階細かい粒度に落とす」ことが今回のゴールで、大きなブロック（フェーズ）に分解し、
各フェーズ完了後に新旧ロジック混在状態でもアプリが正常動作することを担保する。

## 元の依頼内容

このプロダクトについて、Vercel社のv0を使ってデザインを作った。
カレンダー画面について、作ったデザインを踏襲したい。


まずsteeringディレクトリを作ったら、その直下で以下にシンボリックリンクを張り、同じくディレクトリ直下に.gitignoreを作り、このシンボリックリンクをgit管理化から外してほしい
~/src/github.com/tumeda1992/nanitabe_v0_design

まず今回の依頼は、でかすぎるタスクを、1段階細かい粒度のタスク群に落とすこと。
全部移行するのは一気にやってはいけない。大きなブロックに分解して、そのブロックを、ほかでタスクリスト作って実装したい。

大きなブロックが、それぞれ終わった段階では、新旧ロジックおりまぜて全体としてちゃんと動くようにしたい。
つまり、細かいタスクでもイテレーティブに作るけど、それの大きな粒度版でタスク設計をしたい。

進め方の考え方としては
- デザイン外のビジネスロジックについては既存のものを踏襲する
    - デザイン側では、フロントエンドだけで完結するよう、ローカルストレージを使ったけど、本運用ではもちろん、GraphQLを使ってサーバサイドと連携する
- 既存のコンポーネント構成を活かせるなら活かす
    - 既存のコンポーネントディレクトリを使い回せる場合oldディレクトリ運用
        - まずあるコンポーネントoldディレクトリに元々のコンポーネントを移し、その状態で移動前と同じように動くよう修正する
        - その後元々コンポーネントがあったところで、新コンポーネントを作る
    - 既存コンポーネントディレクトリの流用が難しいコンポーネントについては、新コンポーネントディレクトリを作る
    - tips
        - newディレクトリはつくらない
            - いつnewディレクトリから外すかの運用を考えたくないから

また今回のスコープについて
- カレンダーの見え方だけ対象
- backendは触らない
- まだできていない機能やフィールドがあるけれども、それはnullを入れたり、disableにしておく
- 料理検索もこのタスクでは触らない
- プレースホルダーについてはまだビジネス側が実装していないから、作らなくて良い

## 要件

### 要件1: カレンダー見た目の v0 デザイン踏襲
**ユーザーストーリー:** ユーザーがカレンダー画面を開いたとき、v0 で作ったデザイン（ヘッダー・週ビュー・月ビュー・料理カード）と同じ見た目が表示される

#### 受け入れ基準
1. WHEN ユーザーがカレンダー画面を開く THEN v0 デザインと同等のヘッダー（前後ナビ・週月切替・ドロップダウンメニュー）が表示される
2. WHEN 週ビューを表示する THEN 各日付がカード形式（rounded-xl border）で縦に並ぶ
3. WHEN 月ビューを表示する THEN 7列グリッドでカレンダーが表示される
4. WHEN 料理が登録されている THEN 左カラーバー付きカード（昼=lunch色、夜=dinner色）で表示される
5. WHEN アクションを開く THEN 既存操作（削除・移動・交換・料理割当）がアクションパネルに表示される

### 要件2: 既存ビジネスロジック維持
**ユーザーストーリー:** デザイン刷新後も、既存の GraphQL 連携・食事登録・削除・移動・交換などの操作が引き続き動く

#### 受け入れ基準
1. WHEN 食事を追加する THEN 既存の GraphQL mutation (addMeal等) が呼ばれる
2. WHEN 食事を削除する THEN 既存の removeMeal mutation が呼ばれる
3. WHEN 食事を移動・交換する THEN 既存の swapMeals mutation が呼ばれる
4. WHEN 料理を割り当てる THEN 既存の AssignDish フローが動く

### 要件3: 段階移行・各フェーズで動作保証
**ユーザーストーリー:** 各大ブロック完了後に本番環境へデプロイしても、アプリが正常に動作する

#### 受け入れ基準
1. WHEN 各フェーズが完了する THEN 既存テストが全てグリーン
2. WHEN 各フェーズが完了する THEN カレンダー画面が新旧混在状態でも正常表示される

# 設計ドキュメント

## TL;DR

v0 デザイン（Tailwind + shadcn/ui）を既存フロントエンド（Bootstrap + SCSS modules + Apollo GraphQL）に段階移行する。
5つの大ブロック（技術基盤 → アプリシェル → 週ビュー → 月ビュー → 料理カード）に分解し、
各ブロック完了時点でアプリが正常動作する状態を保つ。
localStorage（v0）は GraphQL（本番）に置き換える。プレースホルダー・料理検索はスコープ外。

## 変更点サマリ

| レイヤ | 現状 | 移行後 |
|--------|------|--------|
| UIライブラリ | Bootstrap + SCSS modules | Tailwind CSS + shadcn/ui を追加（共存） |
| カレンダーページ | /calender/week と /calender/month が別ページ | 統合画面（週/月タブ切替）に変更 |
| 週ビューレイアウト | table 形式（Calender/index.tsx） | DayColumn カード形式（縦リスト） |
| 月ビューレイアウト | 週ビューと同じ Calender/index.tsx を使用（保守不足で崩れ気味） | 週ビューと同デザイン（DayColumn カード縦リスト）に刷新 |
| 料理カード | MealIcon（アイコン+FloatModal） | DishCard（左カラーバー+展開アクションパネル） |
| データソース | GraphQL | GraphQL（変わらず。v0のlocalstorageは使わない） |

## 設計選択と理由

### Tailwind + shadcn/ui を追加導入
v0 デザインは Tailwind utility class を多用しており、Bootstrap/SCSS のみで再実装するとコストが大きい。
Next.js への Tailwind 追加は標準的な手順で完了でき、Bootstrap と CSS specificity で共存可能。
shadcn/ui は Radix UI ベースのコピーベースライブラリなので既存コードへの影響が小さい。

### oldディレクトリ運用
ユーザー指示に従い、既存コンポーネントの置き換えでは old/ サブディレクトリを使う。
- `Calender/old/` ← 既存 `Calender/index.tsx` 等を移動
- `MealIcon/old/` ← 既存 `MealIcon/index.tsx` 等を移動
- 元の場所に新コンポーネントを作成

### データフロー
v0 の `MealPlannerProvider`（localStorage）は使わない。
既存の `useMeal` hook + Apollo GraphQL をそのまま使う。
新コンポーネントは props 経由で meal データを受け取る設計にする。

### 未実装機能の扱い
- 料理評価（Star）→ 既存の `dish.evaluationScore` を流用して実装（disabled ではない）
- 料理複製（CopyPlus）→ `onDuplicateMeal={undefined}` で disabled
- 料理検索（DishPickerDrawer）→ スコープ外、既存の AssignDish フローを流用
- プレースホルダー（MEAL_PLACEHOLDER）→ 実装しない

## 代替案と棄却理由

### 代替案1: Bootstrap/SCSS のみで v0 デザインを再実装
v0 の Tailwind クラスをそのまま使えず、全クラスを SCSS に書き直す必要がある。
工数が大きく、v0 デザインとの乖離リスクも高いため棄却。

### 代替案2: フロントエンド全体を v0 プロジェクトとして作り直し
既存の GraphQL 連携・認証・その他画面まで移行が必要になり、スコープが大きすぎるため棄却。

### 代替案3: 一気に全コンポーネントを移行
リスクが高く、途中でデプロイできない状態になるため棄却。段階移行を採用。

## リスクと対策

| リスク | 対策 |
|--------|------|
| Tailwind と Bootstrap の CSS 競合 | CSS layer/specificity を調整。Tailwind の `important` や preflight の無効化 |
| 既存 SCSS との混在 | 段階移行なので混在は一時的。フェーズごとに旧 SCSS を削除 |
| GraphQL データ構造と v0 型の不一致 | v0 の型定義は使わず、既存 GraphQL 型（MealForCalender等）を使う |
| old/ 移動後のインポートパス修正漏れ | 移動直後に既存テスト・ESLint でエラー検出 |

## テスト方針

- 各フェーズ完了時: `docker compose exec frontend yarn test` で全テストグリーン確認
- ESLint: `docker compose exec frontend yarn lint` でエラーゼロ確認
- 既存テスト（Menu.spec.tsx等）は old/ 移動後もパスを修正して維持
- 新コンポーネントに最小限のユニットテスト（表示確認レベル）を追加
