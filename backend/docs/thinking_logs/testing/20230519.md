# 方針
オレオレ実装のcomparerを使ってテストする

# 背景
RSpecの制約によって、当たり前のようにやりたいことができないことが多い。

- letで定義したものをどこでも呼べない
  - (記載が2025/8/11で何が辛かったか覚えてないから、思い出したら書く)
- テスト前で共用したいものはbeforeやsubjectで書かなければいけないが、そこで定義したものをitの中で共用しにくいなどがある
  - (記載が2025/8/11で何が辛かったか覚えてないから、思い出したら書く)

これによってテストの使いまわしで辛くなる

## なぜテストを使い回すのか
### 同じロジックを裏で使うユースケースが多い
今回のシステムだと、「料理だけ新規作成してレシピ元は既存のものを使う」「料理とレシピ元どちらも新規作成」とかのユースケースがあり、
どちらもちゃんとレコードができていることとかを自動テストで保証し続けたい。

## 使い回すことが前提の辛さ
- それぞれのテストで個々に保証してもいいが、すると、1個変えたときに全テストを変えなければならないとかがn重管理になる。
- 期待値用意も含めた事前準備が楽だと嬉しかった

そのためテストの使い回しがしやすい形がよかった

# テスト実装方法
## テスト下準備
```ruby
require_relative "../../../../../../support/factories/user_repository"
require_relative "../../../../../../support/factories/dish_repository"

KEY_OF_TEST_DISH_TAG_SHOULD_BE_CREATED = "DISH_TAG_SHOULD_BE_CREATED"
comparer = ExpectationComparer.new(KEY_OF_TEST_DISH_TAG_SHOULD_BE_CREATED, {
  content: "白ワインに合う",
  normalized_content: "白ワインニ合ウ",
})

comparer.define_required_records_for_test do
  {
    user_record: find_or_create_user(),
    dish_record: find_or_create_dish(),
  }
end

comparer.define_expectation do |expected_values, prepared_records|
  added_dish_tag_record = ::DishTag.last
  expect(added_dish_tag_record.user_id).to eq prepared_records[:user_record].id
  expect(added_dish_tag_record.dish_id).to eq expected_values[:dish_id] || prepared_records[:dish_record].id
  expect(added_dish_tag_record.content).to eq expected_values[:content]
  expect(added_dish_tag_record.normalized_content).to eq expected_values[:normalized_content]
end

COMPARERS[comparer.key] = comparer
```

### comparerの起動と期待値定義
```ruby
KEY_OF_TEST_DISH_TAG_SHOULD_BE_CREATED = "DISH_TAG_SHOULD_BE_CREATED"
comparer = ExpectationComparer.new(KEY_OF_TEST_DISH_TAG_SHOULD_BE_CREATED, {
  content: "白ワインに合う",
  normalized_content: "白ワインニ合ウ",
})

COMPARERS[comparer.key] = comparer
```
- 期待値を定義して、テスト側と共用できるようにする
- 読み込み時に定義しておくことで、rails_helperを読み込んでおけば使えるようにする

### データ準備
```ruby
require_relative "../../../../../../support/factories/user_repository"
require_relative "../../../../../../support/factories/dish_repository"

comparer.define_required_records_for_test do
  {
    user_record: find_or_create_user(),
    dish_record: find_or_create_dish(),
  }
end
```
- 起動時点でデータを作っておく
- データ作成には、FactoryBotを利用すると必ずデータ作成を作ってしまい、既存データを使いたいときに本意ではないので、repositoryでラッピングしている

```ruby
# spec/support/factories/user_repository.rb
ID_PARAM_OF_USER ||= "userrrrrrrrrrrrrrr".freeze

def find_or_create_user
  ::User.find_by(id_param: ID_PARAM_OF_USER) || FactoryBot.create(:user)
end

# spec/support/factories/users.rb
require_relative "./user_repository"

FactoryBot.define do
  factory :user do
    id_param { ID_PARAM_OF_USER }
  end
end
```

### 期待値チェッカー
```ruby
comparer.define_expectation do |expected_values, prepared_records|
  added_dish_tag_record = ::DishTag.last
  expect(added_dish_tag_record.user_id).to eq prepared_records[:user_record].id
  expect(added_dish_tag_record.dish_id).to eq expected_values[:dish_id] || prepared_records[:dish_record].id
  expect(added_dish_tag_record.content).to eq expected_values[:content]
  expect(added_dish_tag_record.normalized_content).to eq expected_values[:normalized_content]
end
```

- 変更や作成されたレコードを取得して期待値と比較する
- expected_valuesは最初に定義した期待値だけでなく、define_expectation実行時に差し込めば期待値を変えることができる

## テスト実装
```ruby
# frozen_string_literal: true

require "rails_helper"
require_relative "./repository_add_shared_examples"

module Business::Dish::Dish::Tag
  RSpec.describe Repository do
    describe ".add" do
      before do
        comparer.build_records_for_test()

        @dish_tag = Tag.new(
          user_id: comparer.prepared_records[:user_record].id,
          dish_id: comparer.prepared_records[:dish_record].id,
          **comparer.values
        )
      end

      context "when add dish tag with required fields," do
        let!(:comparer) { COMPARERS[KEY_OF_TEST_DISH_TAG_SHOULD_BE_CREATED] }

        it "adding succeeds" do
          described_class.add(@dish_tag)

          comparer.compare_to_expectation(self)
        end
      end
    end
  end
end
```

- comparerで定義したものをただ単に使えば終わり。
- これがあるデータ単体で作るときだと効果を発揮しづらいが、この処理をラッピングする仕組みでも同じく読み込むだけで簡潔にテストができる

# メリデメ
メリット
- 使い回しが容易
- 1箇所変えれば使っているところ全体が変わってくれる
- 厚いテストをE2Eでも行うのに手間が少ない
  - そもそもE2Eなどの上位ではテストする必要がないというのが実態だとは思う
  - だけど入れ子構造で同じテストロジックをコピペして作らないといけないと手間だからやらない方に倒す重力が働く
  - 最低限、DBのデータがinput（ラッピングしたところで利用したinput）と同様に入ったかくらいは確認したかった。バリエーションは下位のテストに任せるにせよ

デメリット
- 実装がオレオレすぎる
- ある場所で値や特有で変えたいときに影響範囲が大きい
