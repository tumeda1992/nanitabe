# 基本方針
DDDの考え方を基本方針にしている。

## レイヤードアーキテクチャ
次のようなレイヤを組んでいる

- プレゼンテーション層
  - railsのcontrollerやGraphQLなど、ユーザからのリクエストを受け取ってレスポンスを返す
  - 入力値レベルのバリデーションを行う
  - **異なる集約をまたぐオーケストレーションはこの層が担う**
    - 例: Dish の作成（`Dish::Usecase::AddCommand`）と Meal の作成（`Meal::Usecase::AddCommand`）を組み合わせる処理は resolver が順に呼ぶ
    - 理由: 異なる集約を1つの Command に内包するとドメイン境界が崩れる。Command は自分の集約の範囲内でのみオーケストレーションする
  - **集約ルートと子エントリが不可分な場合、resolver が1トランザクションで親+全エントリを作成・置換する**
    - MUST: フロントエンドが「親を作る mutation → 子を作る mutation × N」と複数回呼ぶ設計は禁止
    - 理由: mutation をまたいだ `ActiveRecord::Base.transaction` は機能しない。途中失敗で親だけ作られ子が欠ける部分適用が起きる
    - やってしまいがちな失敗: 親と子を別集約として捉え個別 mutation を設計する → フロントエンドのオーケストレーション責務になりトランザクション保証を失う
    - 適用例: `addMealFramePattern(name, entries[])` — Pattern と全 PatternEntry を1 mutation・1トランザクションで完結
- ユースケース層
  - ドメイン層の外からドメインロジックを実行する
  - DDDにおけるアプリケーションサービスがその役割を担う
    - データに対して副作用があるものをCommand、副作用がないものをQueryとして分ける
    - Commandはオーケストレーションのみ担い、ビジネスロジックをCommand内に書くことは禁止（置き場所は「ドメインロジックの置き場所」セクションを参照）
    - **Command のオーケストレーション範囲は自集約の内部に限定する**（異なる集約をまたぐ場合はプレゼンテーション層が担う）
    - 複数件処理するBulkコマンドは単一件CommandへのオーケストレーションのみとしBulk内にロジックを書かない
  - ドメイン層へ入る上でのバリデーションを行う
- ドメイン層
  - ドメインロジックを実行する
  - 個々のモデルでのバリデーションは行うが、入力値はバリデーション済みとして扱う
  - メソッド命名規則:
    - MUST: メソッド名はドメインの「行為・意図」を表す動詞にする
      - 良い例: `rename`（名前を変える）、`reposition_in_meal`（食事での位置を変える）、`assign_effort_level`（手間レベルを割り当てる）
      - 悪い例: `set_name`、`change_position`、`update_effort_level`
    - MUST: `set_xx` / `change_xx` / `update_xx` のような汎用的な変更操作名は禁止
    - 命名の問いかけ: 「このメソッドはドメインで何が起きているか」を名前で伝えられているか
- インフラストラクチャ層
  - DB接続や外部API接続などを行う

## 実装コストを理由にユーザー体験を変えてはならない

実装変更の提案前に、その変更がユーザー体験（機能・振る舞い）に影響するかを確認すること。

- 体験が変わらない（内部実装の置き換え・リファクタリング）→ 既存コードの削除・統合を許容
- 体験が変わる（機能・振る舞いが変わる）→ 実装コストを理由に変更してはならない

やってしまいがちな失敗: 「これを消せば実装が楽になる」という理由で、ユーザーが使っている機能・要素を削除する案を出す
→ 正しい問い: 「この変更はユーザーが体験できることを変えるか？」→ Yes なら実装コストは理由にならない

## 共通化（抽出）の判断基準

コードが同一に見えることは、共通化の十分条件ではない。

判断の問い: **「Aの要件が変わったとき、Bも同じ理由で変わるべきか？」**
- Yes（変更の必然性がある）→ 抽出して共通化する
- No（独立したコンテキストにある）→ たとえ同一コードでも別々に持つ

同一コードなのに抽出しないのはなぜか:
- 共通化した瞬間に独立していた2つが依存関係を持つ
- 片方の要件変更が他方に波及し、意図しない変更が必要になる
- 差異を吸収するためにオプション・分岐が生えて関数が肥大化する
- 「やはり分けよう」となったとき、使用箇所を探して剥がす作業が発生する

コードの重複はコストだが、誤った抽出はより高いコストになる。

やってしまいがちな失敗（逆パターン）: 「コンテキストが違う」「実装が少し違う」という理由で、変更タイミングが同じコードをコピペ展開する
→ 同じ理由で同じタイミングで変わるコードが2箇所にあると、片方の変更漏れが起きる
→ 判断の問い: 「このコードを変えるとき、もう一方も必ず同じ理由で変わるか？」→ Yes なら抽出する

## ドメインモジュール帰属の判断基準

判断の問い: **「このエンティティは、既存のドメイン概念の文脈を外れても意味を持つか？」**

- Yes（独立したドメイン概念として機能する）→ 新しいトップレベル集約として追加する
- No（既存の概念の文脈でのみ意味を持つ）→ 既存モジュール下に置く

トップレベルへの追加が重い理由:
- トップレベルモジュール = 「このプロジェクトの主要なドメイン概念」の宣言になる
- 誤ってトップレベルに置くと「AとBは別のもの？」という認識ズレが永続する
- 後から修正するとき名前空間変更の影響範囲が広い

やってしまいがちな失敗: 「別テーブルがある → 新しいトップレベルモジュールを作る」と短絡する

やってしまいがちな失敗（サブ概念追加時）: 既存モジュールに関連する新サブ概念を追加するとき、「この概念は既存モジュールの文脈を外れても意味を持つか？」を問わずにトップレベルに並べてしまう
→ 例: `Meal::Frame::Pattern` は `Frame` なしには意味を持たない → `Meal::Frame::Pattern::Root` が正しく、`Meal::FramePattern::Root` は誤り

## ドメインロジックの置き場所

MUST: ドメインロジックは常にドメイン層に置く。置き場所の判断は以下の順で行う。

**1. 既存集約の振る舞いとして表現できるか？**
- 単一の既存集約の振る舞い → その集約のメソッドとして実装する
- 複数の集約にまたがるオーケストレーション → プレゼンテーション層が担う（「レイヤードアーキテクチャ」参照）
- いずれでもない → 次の問いへ

**2. 保存前のビジネス状態を表現する新しいドメイン概念が必要か？**（→「集約を作る判断基準」参照）
- Yes → 新規集約（Root）を作る
- No → 値オブジェクト・Policy として表現する
  - 値オブジェクト: 不変の値の表現（同一性を持たない）
  - Policy: 適用可否・資格の判定（例: `AttachDishPolicy`）

やってしまいがちな失敗: 「新しい集約がないからCommandに書く」→ ドメイン貧血症を引き起こす

## 集約を作る判断基準

判断の問い: **「保存前のビジネス状態を表現するドメインオブジェクトが必要か？」**

- Yes → 集約（Root）を作る
- No → 値オブジェクト・Policy として表現する（「ドメインロジックの置き場所」参照）

テーブル構造は集約設計の根拠にならない。

やってしまいがちな失敗: 「別テーブルがある → 集約を作る」と短絡する
→ ビジネスロジックのない空洞の集約が量産され、ドメインとインフラの境界が崩れる

## 命名の判断基準

判断の問い: **「この名前は、このエンティティが本質的に何であるかを伝えているか？」**

- 命名の根拠は「このエンティティ・テーブルは本質的に何であるか（何を表すものか）」に置く
- 「現在の他の命名との整合性」は命名の根拠にならない

テーブル・クラス名・モジュール名は変更コストが高く長期間存在する。現状のコード命名パターンとの整合性を根拠にした命名は、将来の認識ズレを固定化する。

やってしまいがちな失敗: 「現在の他の命名との整合性がある」という理由で命名する
→ 例: 「複数日の枠配置の構造」を表す概念を、「型として使う」という用途から `template` と命名する
→ 正しい問い: 「このエンティティは本質的に何か？」→ 配置の「パターン」が本質的な名前
→ テーブルは長生きする。現状のコードより本質が長く正しい

### 命名の検証手法: 将来進化テスト

「本質的な名前か」を検証するために、将来の進化パターンを**異なる方向に複数**列挙し、それぞれで命名が金属疲労するかを確認する。

手順:
1. 現状のオペレーションの本質から候補の名前を決める
2. 「現実的にありえる進化例」を**異なる方向に 3〜4 つ**列挙する（1つの方向に偏らせない）
3. 各進化例に対して「この命名は自然に通用するか？」を確認する
4. 複数の方向で金属疲労するなら、現状のオペレーションも含めてそれらの進化も自然に通る命名を再検討する

MUST: 進化例は「検証」に使うのであって「命名の根拠」にしてはならない
- 特定の進化例に特化した命名は、現状のオペレーションをないがしろにすることになる
- やってしまいがちな失敗: 「いつかサイクル機能を追加するから `Routine` にしよう」→ 現状無視の命名

適用例（`template` vs `pattern`）:
- 進化例a: 繰り返し適用（サイクル） → `template`: やや違和感、`pattern`: 自然（サイクルもパターン）
- 進化例b: 他ユーザーとの共有 → 両方通用
- 進化例c: 適用履歴の保存 → `template`: やや違和感、`pattern`: 自然（パターンが適用された履歴）
→ 複数方向で `pattern` が通用し、かつ現状（複数日の枠配置の構造）も内包 → 本質的な命名として確認

## データモデリングの判断基準

### フィールド追加の判断基準

判断の問い: **「このエンティティはこのフィールドなしで完結した意味を持つか？」**

- Yes → フィールドを追加しない。そのフィールドが必要になる文脈を別エンティティとして切り出す
- No（このエンティティの定義に属する）→ フィールドとして追加する

やってしまいがちな失敗: 後から必要になったフィールドを既存エンティティに nullable で追加する
→ エンティティの不変条件が薄まり、「null = 未設定」なのか「null = 不要」なのかが曖昧になる

### FK の向きの判断基準

判断の問い: **「このエンティティは、関連先なしで独立して存在できるか？」**

- Yes（独立して存在できる）→ FK を持たない。関連付けの責務は、関連付けのために存在するエンティティが担う
- No（関連先ありきで存在する）→ FK を持つ

やってしまいがちな失敗: 独立して存在できるコアエンティティに nullable FK を追加して関連を表現する
→ 「FK が null = 未割当」「FK が null = 関連なし」の意味が曖昧になる

## 一般的なDDDとの違い
- リポジトリの役割としてActiveRecordを使う
  - RailsのActiveRecordはORマッパーとしてリポジトリの役割を果たしているため、ことさらRepositoryを置かない
    - 必要になったらまずはそこだけRepositoryを用意する
    - リポジトリの役割を担うため、ActiveRecord単体で完結しないで、集約などドメインモデルなどを知っていることを許容
  - ただし、外部API接続などはインフラストラクチャ層に置く

### Root 属性と ActiveRecord カラムの非同期

Root の attribute と ActiveRecord のカラムは自動同期しない。
Root に属性を追加するときは以下の2箇所も必ず連動して変更すること:

- `build_existing_root_from_id`（DB → Root のマッピング）
- `persist_from_xxx_root`（Root → DB の保存）

やってしまいがちな失敗: `root.rb` に attribute を追加したが persist を更新し忘れ、属性が保存されない（エラーも出ない）。
例: `FrameEntry::Root` に `meal_id` attribute を追加する際、`persist_from_food_meal_frame_entry_root` を更新しないと `meal_id` が DB に保存されない。
